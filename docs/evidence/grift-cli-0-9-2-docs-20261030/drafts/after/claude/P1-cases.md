0.9.2からは、grift-cliのリポジトリをcloneして作ったDockerのイメージで、griftを実行できます。ホストにPythonを入れる必要はありません（例: `docker build -t grift-cli grift-cli`、`docker run --rm -v "$PWD:/repo:ro" grift-cli repo`）。読みたいリポジトリは`/repo`にmountし、履歴は全部取得しておきます。shallow cloneをmountすると、渡されたcommitだけで数え、`revision_completeness`が`complete: false`になります。`git worktree`で作った作業ツリーはコンテナ内から履歴を読めず、exit 2で止まるため、mountしません。`--out`で書き出すときは`--user "$(id -u):$(id -g)"`を付けます。イメージに入れるのは`git`と`openssh-client`だけです。`gh`と`cosign`は入れないため、`contribute --open`とcosignを呼ぶ操作はホスト側で実行します。`grift update`は、実行中のgrift-cliの環境を明示的に更新し、更新後の版を表示します。実行中の環境がpipxの管理ならpipxで、それ以外は実行中のPythonの`-m pip`で更新します。PATHにある別の環境のpipは使いません。`grift update --check`はPyPIの最新版の情報を読むだけで、更新はしません。`grift --version`は通信せずに手元の版を表示します。自動の更新はなく、ふだんの測定コマンドが版を確かめる通信もしません。通信できないときや更新に失敗したときは、メッセージを出します。`grift contribute`は、本人が同意したあとに`.grift/contribution.json`を保存します。表示するのは、提出ID、PRに入れるファイル名、保存したバイト列のSHA-256を含むmetaとmanifestの行、2つの提出経路のURLです。自動では送りません。本人の公開PRの経路でも、身元を伏せる代理PRの経路でも、payloadそのものは公開されます。既定の`--door local`で作ったv2のpayloadは、公開の受け口に出せません。公開して出すときは`--door public-pr`で作り直し、新しく表示されたID・hash・metaを使います。リポジトリの文脈には、初めて活動した年と最後に活動した年、タグの頻度の分子と分母が出ます。`actor_turnover`の`joined`は、観測した履歴で初めて活動した年です。`last_active`は最後に活動した年で、今も活動している人も入ります。そのため、離脱や退職を示すものではありません。`release_cadence`は「タグ数÷活動の期間の日数×365.25」で年に換算した値（tags/year）です。たとえば43タグ・70日なら224.37 tags/yearですが、224回のリリースを観測したという意味ではありません。

[0.9.2](https://github.com/Cor-Incorporated/grift-cli/releases/tag/v0.9.2)では、Dockerfileを足し、ホストにPythonを入れずにgriftを実行できるようにしました。CIにもdockerのjobを足し、イメージの`--version`と、読み取り専用のmount・networkなしでの`repo`の観測を確かめます。Dockerで実行しても、コマンドと出力は変わりません。あわせて、`grift update`、`grift contribute`、リポジトリの文脈の年とタグの頻度を、上に書いた形にしました。利用規範のとおり、点数・順位・合否を出さないことは0.9.2でも変わりません。
