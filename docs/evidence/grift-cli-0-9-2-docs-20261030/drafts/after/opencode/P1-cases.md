[0.9.2](https://github.com/Cor-Incorporated/grift-cli/releases/tag/v0.9.2)では、griftを動かせる場所と、更新と提出のしかたが増えました。Dockerfileを足しました。ホストにPythonを入れなくても、grift-cliのリポジトリをcloneして作ったイメージでgriftを実行できます。イメージは`docker build -t grift-cli grift-cli`で作ります。読みたいリポジトリは`/repo`にmountして、`docker run --rm -v "$PWD:/repo:ro" grift-cli repo`のように実行します。shallow cloneをmountすると、渡されたcommitだけで数えます。`revision_completeness`が`complete: false`になります。履歴は全部取得しておく必要があります。`git worktree`で作った作業ツリーはmountできません。コンテナの中から履歴を読めず、exit 2で止まります。`--out`で書き出すときは、`--user "$(id -u):$(id -g)"`を付けます。イメージに入れるのは`git`と`openssh-client`だけです。`contribute --open`と、cosignを呼ぶ操作はホスト側で実行します。CIでも、イメージの`--version`と、読み取り専用のmount・networkなしでの`repo`の観測を確かめています。コマンドと出力は変わりません。`grift update`は、実行中のgrift-cliの環境を明示的に更新し、更新後の版を表示します。実行中の環境がpipxの管理なら、pipxで更新します。それ以外は実行中のPythonの`-m pip`で更新します。PATHにある別の環境のpipは使いません。`grift update --check`はPyPIの最新版の情報を読むだけで、更新はしません。`grift --version`は通信せず、手元の版を表示します。自動の更新と、ふだんの測定コマンドからの版の確認の通信はありません。通信できないときや更新に失敗したときは、メッセージを出します。`grift contribute`は、本人が同意したあとに`.grift/contribution.json`を保存します。表示するのは、提出ID、PRに入れるファイル名、2つの提出経路のURLです。保存したバイト列のSHA-256を含むmetaとmanifestの行も表示します。自動では送りません。既定の`--door local`で作ったv2のpayloadは、公開の受け口に出せません。公開して出すときは、`--door public-pr`で作り直します。新しく表示されたID・hash・metaを使ってください。本人の公開PRの経路も、身元を伏せる代理PRの経路も、payloadそのものは公開されます。

[0.9.2](https://github.com/Cor-Incorporated/grift-cli/releases/tag/v0.9.2)では、リポジトリの文脈（context profile）に、初めて活動した年と最後に活動した年、タグの頻度の分子と分母を出すようにしました。`actor_turnover`の`joined`は観測した履歴で初めて活動した年です。`last_active`は最後に活動した年です。今も活動している人も`last_active`に入るため、離脱や退職を示すものではありません。`release_cadence`は「タグ数 ÷ 活動の期間の日数 × 365.25」の年換算（tags/year）です。43タグ・70日なら224.37 tags/yearになりますが、224回のリリースを観測したという意味ではありません。点数・順位・合否を出さないことは、0.9.2でも変わりません。
