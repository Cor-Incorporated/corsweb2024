0.9.2ではDockerでもgriftを実行できます。ホストにPythonを入れずに、grift-cliのリポジトリをcloneして作ったイメージ（`docker build -t grift-cli grift-cli`）で動かし、読みたいリポジトリは`/repo`にmountします（`docker run --rm -v "$PWD:/repo:ro" grift-cli repo`）。mountするリポジトリは履歴を全部取得しておきます。shallow cloneでは渡されたcommitだけで数えるため、`revision_completeness`が`complete: false`になります。`git worktree`で作った作業ツリーはコンテナの中から履歴を読めず、exit 2で止まるため、mountしません。`--out`で書き出すときは`--user "$(id -u):$(id -g)"`を付けます。イメージには`git`と`openssh-client`だけを入れ、`gh`と`cosign`は入れていないので、`contribute --open`とcosignを呼ぶ操作はホストで実行します。`grift update`は実行中のgrift-cliの環境を明示的に更新し、更新後の版を表示します。pipxで管理している環境はpipxで、それ以外は実行中のPythonの`-m pip`で更新し、PATHにある別の環境のpipは使いません。`grift update --check`はPyPIの最新版の情報を読むだけで、更新はしません。`grift --version`は通信せずに手元の版を表示します。自動で更新するための通信も、ふだんの測定コマンドが版を確かめるための通信もありません。通信できないときや更新に失敗したときは、メッセージを出します。`grift contribute`は、本人が同意したあとで`.grift/contribution.json`を保存し、提出ID、PRに入れるファイル名、保存したバイト列のSHA-256を含むmetaとmanifestの行、2つの提出経路のURLを表示します。自動では送りません。既定の`--door local`で作ったv2のpayloadは公開の受け口に出せないため、公開して出すときは`--door public-pr`で作り直し、新しく表示されたID・hash・metaを使います。本人の公開PRの経路でも、身元を伏せる代理PRの経路でも、payloadそのものは公開されます。リポジトリの文脈には初めて活動した年と最後に活動した年、タグの頻度の分子と分母を表示します。初めて活動した年（`actor_turnover`の`joined`）は観測した履歴の中での年です。最後に活動した年（`last_active`）には今も活動している人も入るため、離脱や退職を示すものではありません。タグの頻度（`release_cadence`）は、タグ数を活動の期間の日数で割って365.25を掛けた年換算（tags/year）です。たとえば43タグ・70日なら224.37 tags/yearですが、224回のリリースを観測したという意味ではありません。

[0.9.2](https://github.com/Cor-Incorporated/grift-cli/releases/tag/v0.9.2)では、ホストにPythonを入れずに、Dockerでgriftを実行できるようにしました。Dockerで動かしても、コマンドと出力は変わりません。CIにDockerのjobを足し、イメージの`--version`と、読み取り専用のmount・networkなしでの`repo`の観測を確かめています。`grift update`による更新、`grift contribute`による提出、リポジトリの文脈の表示も、上に書いた形にしました。点数・順位・合否を出さないことは変わりません。
