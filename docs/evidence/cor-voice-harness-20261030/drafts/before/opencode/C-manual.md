# cor-jp.com のブログ記事を新しく書いて、公開の準備をするまで

## この手順書について

この手順書は、cor-jp.com のブログ記事を新しく書き、公開の準備ができるところまでをまとめたものです。エンジニアでない方でも、上から順に進められるように書いています。

この手順書で扱うのは「記事を書いて、検査を通して、公開の準備を整える」ところまでです。**merge（統合）と公開は代表が行います。** あなたが最後までやることはありません。

### 全体の流れ

| 順番 | やること | 主に誰がやるか |
|---|---|---|
| 1 | 管理画面で記事を書き始める | あなた |
| 2 | frontmatter（記事の頭に付ける設定欄）を埋める | あなた |
| 3 | 本文を書く | あなた |
| 4 | 文言の検査をする | あなた（コマンドはエンジニアに頼んでもよい） |
| 5 | 推敲の検査をする | あなた（同上） |
| 6 | develop 向けの PR を確認し、翻訳が付くのを待つ | あなた（翻訳は CI が行う） |
| 7 | ビルドが通ることを確かめる | あなた／エンジニア |
| 8 | 代表に merge と公開を頼む | あなた → 代表 |

### 用語をかんたんに

- **管理画面（Sveltia CMS）**: ブラウザから記事を書ける画面です。https://cor-jp-cms-admin.web.app/
- **frontmatter**: 記事のいちばん上にある設定欄です。タイトルや日付などをここに書きます。
- **PR（プルリクエスト）**: 「この変更を取り込んでください」という依頼のまとまりです。今回は develop 向けに作られます。
- **CI**: 自動で動く仕組みです。今回は翻訳を作る担当です。
- **develop / main**: 作業用の置き場（develop）と、本番に出る置き場（main）です。

---

## 手順 1. 管理画面で記事を書き始める

1. ブラウザで https://cor-jp-cms-admin.web.app/ を開きます。
2. ブログの記事の新規作成を選びます。
3. 記事名を付けます。この名前が `src/content/blog/ja/<記事名>.md` のファイル名になります。あとから変えると分かりにくくなるので、先に決めておきましょう。
4. 保存します。**保存すると、develop 向けの PR が自動でできます。** この PR が、公開準備の単位になります。

> エンジニアの方は、`src/content/blog/ja/<記事名>.md` を直接作ってもかまいません。その場合も、以降の手順は同じです。

---

## 手順 2. frontmatter（設定欄）を埋める

記事のいちばん上にある設定欄を埋めます。**必須の項目はすべて入れてください。**

### 必ず入れる項目

| 項目 | 入れる内容 |
|---|---|
| `title` | 記事のタイトル |
| `description` | 記事の短い説明。**空にしない** |
| `pubDate` | 公開日 |
| `category` | `ai`、`engineering`、`founder`、`lab` のどれか 1 つ |
| `tags` | タグ |
| `author` | `"Terisuke"` |
| `lang` | `"ja"` |

### 任意で入れられる項目

| 項目 | 入れる内容 |
|---|---|
| `summary` | 2〜3 文の要約。記事の上の「この記事の要点」として表示されます |
| `image` | 記事の画像 |

`category` は上の 4 つ以外を書かないでください。`description` が空だと、あとの手順 7 のビルドで落ちます。

---

## 手順 3. 本文を書く

1. 本文を書きます。
2. **出典は、本文の最後に「## 参考資料」という見出しを作り、リンクの箇条書きで置きます。**
3. **本文の中に営業の誘い文句は入れません。**

### ISMS について書くときの言い方

ISMS に触れる記事では、書いてよいのは次のところまでです。

- 「2026年10月に ISO/IEC 27001 の第2段階審査を終え、2026年12月ごろの認証登録を見込んでいる」

**「取得済み」とは書きません。** 認証の登録が終わるまでは、取得したとは書けない決まりです。

---

## 手順 4. 文言の検査をする

書いた記事に対して、決まった言い回しの検査をします。リポジトリのある端末で、次のコマンドを実行します。

```bash
npm run blog:check -- src/content/blog/ja/<記事名>.md
```

`<記事名>` は、実際のファイル名に置き換えてください。

- 指摘が出たら、記事を直してからもう一度実行します。
- コマンドの実行に慣れていない場合は、エンジニアに「この記事の文言検査をお願いします」と頼めば大丈夫です。渡すものは記事のファイル名（`src/content/blog/ja/<記事名>.md`）だけです。

---

## 手順 5. 推敲の検査をする

文章そのものを整えるための検査です。次の順番で進めます。

1. まず、推敲の下準備をします。

   ```bash
   npm run polish -- prepare --file src/content/blog/ja/<記事名>.md
   ```

2. 出てきた内容に沿って記事を書き直します。書き直した最終稿は、作業用のファイルとして `tmp/` の下に保存します。
3. 元の記事と最終稿を突き合わせて検査します。

   ```bash
   npm run polish -- check --file src/content/blog/ja/<記事名>.md --final <最終稿>
   ```

   `<最終稿>` は、手順 2 で `tmp/` の下に保存したファイルの場所に置き換えてください。

4. 指摘が出たら書き直し、手順 3 の検査をもう一度実行します。通るまで 2〜3 を繰り返します。

こちらのコマンドも、エンジニアに頼んで実行してもらってかまいません。

---

## 手順 6. PR を確認し、翻訳が付くのを待つ

1. 手順 1 で保存したときにできた PR が、**develop 向け**になっていることを確認します。
2. 英語・中国語・韓国語・スペイン語の訳は、**PR を develop に出すと CI が作って、その PR に足します。** しばらく待つと訳が追加されます。
3. **訳のファイルは手で直しません。** 訳を直したいときは、日本語の記事の側を直します。

---

## 手順 7. ビルドが通ることを確かめる

次のコマンドで、サイトが問題なく組み立てられるかを確かめます。

```bash
npm run build
```

- frontmatter が間違っていると、ここで落ちます。
- 落ちたときは、まず手順 2 の設定欄を見直してください。`description` が空になっていないか、`category` が 4 つのどれかになっているか、`author` と `lang` が決まった値になっているかを確認します。

---

## 手順 8. 代表に merge と公開を頼む

1. 手順 4・5 の検査が通り、手順 7 のビルドが通ったら、代表に連絡します。伝えるのは「PR の場所」と「検査とビルドが通ったこと」です。
2. **merge と公開は代表が行います。**
3. **develop から main へのリリースで、本番（cor-jp.com）に出ます。** リリースのタイミングも代表が決めます。

---

## やってはいけないこと（まとめ）

- `description` を空にする
- 本文に営業の誘い文句を入れる
- 出典を「## 参考資料」の外に置く
- 英語・中国語・韓国語・スペイン語の訳のファイルを手で直す
- ISMS について「取得済み」と書く（書けるのは「第2段階審査を終え、2026年12月ごろの認証登録を見込んでいる」まで）
- `category` に `ai`、`engineering`、`founder`、`lab` 以外を書く

## 困ったときは

- **コマンドが動かない・実行の仕方が分からない**: エンジニアに、記事のファイル名（`src/content/blog/ja/<記事名>.md`）を伝えて実行を頼みます。
- **`npm run build` が落ちる**: まず frontmatter を見直します（手順 2）。直しても落ちるときは、エンジニアにエラーの内容をそのまま見せます。
- **訳がまだ付かない**: CI が作るので、少し待ちます。待っても付かないときは、PR の画面をエンジニアに見せて相談します。
