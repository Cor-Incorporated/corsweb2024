# cor-jp.com のブログ記事を新しく書いて、公開の準備をするまで

## 1. この手順書について

この手順書は、cor-jp.com のブログに新しい記事を1本追加し、公開できる状態にするまでの流れをまとめたものです。新しく入ったスタッフ向けに、エンジニアでなくても読めるように書いています。

記事を書く方法は2つあります。

- 管理画面（Sveltia CMS、https://cor-jp-cms-admin.web.app/ ）で書く
- エンジニアが `src/content/blog/ja/<記事名>.md` を直接作る

6章の検査ではコマンドを使います。記事のファイルを置いている場所（リポジトリ）を扱える環境での作業です。管理画面で書いた場合も、公開の前にこの検査が必要です。

## 2. 全体の流れ

1. 記事を書く
2. frontmatter を埋める
3. 本文の決まりを守って書く
4. 文言の検査をする
5. 推敲する
6. ビルドが通ることを確かめる
7. develop 向けの PR を用意する（管理画面は保存で自動作成）
8. CI が訳を PR に足すのを待つ
9. 代表が merge し、公開される

## 3. 記事を書く

### 3-1. 管理画面（Sveltia CMS）で書く

1. https://cor-jp-cms-admin.web.app/ を開きます。
2. 新しい記事を作り、本文を書きます。
3. 保存します。

保存すると、develop 向けの PR ができます。PR を自分で作る必要はありません。

### 3-2. エンジニアがファイルを直接作る場合

1. `src/content/blog/ja/<記事名>.md` を作ります。
2. 4章の frontmatter と、5章の本文の決まりにしたがって書きます。
3. develop 向けの PR を出します。

## 4. frontmatter を埋める

frontmatter は、記事の冒頭に置く設定のまとまりです。次の項目を埋めます。

| 項目 | 必須 | 書く内容 |
| --- | --- | --- |
| title | 必須 | 記事のタイトル |
| description | 必須 | 記事の説明。空にしない |
| pubDate | 必須 | 公開日 |
| category | 必須 | `ai`、`engineering`、`founder`、`lab` のどれか1つ |
| tags | 必須 | 記事に付けるタグ |
| author | 必須 | `"Terisuke"` |
| lang | 必須 | `"ja"` |
| summary | 任意 | 2〜3文。記事の上の「この記事の要点」に出る |
| image | 任意 | 画像 |

- description は空にしないでください。
- category は、上の4つのどれか1つを選びます。
- summary は任意です。付けると、記事の上の「この記事の要点」に出ます。
- image も任意です。

## 5. 本文の決まり

- 出典は、記事の最後の「## 参考資料」に、リンクの箇条書きで置きます。
- 本文に営業の誘い文句を入れません。
- ISMS について書くときは、「2026年10月に ISO/IEC 27001 の第2段階審査を終え、2026年12月ごろの認証登録を見込んでいる」までにします。「取得済み」とは書きません。

## 6. 公開前に検査する

ここからのコマンドは、リポジトリで実行します。`<記事名>` と `<記事>` は、実際のファイル名に置きかえます。

### 6-1. 文言の検査

```bash
npm run blog:check -- src/content/blog/ja/<記事名>.md
```

### 6-2. 推敲

1. 次のコマンドを実行します。

   ```bash
   npm run polish -- prepare --file <記事>
   ```

2. 記事を書き直します。
3. 次のコマンドで、推敲の検査をします。`<最終稿>` は、書き直したあとのファイルです。

   ```bash
   npm run polish -- check --file <記事> --final <最終稿>
   ```

### 6-3. ビルド

```bash
npm run build
```

`npm run build` が通ることを確かめます。frontmatter が間違っていると、ここで落ちます。

## 7. PR を develop に向ける

- 管理画面で書いた場合: 保存でできた PR が develop 向けです。新しく作る必要はありません。
- エンジニアがファイルを作った場合: develop 向けの PR を出します。

## 8. 翻訳が PR に足されるのを待つ

PR を develop に出すと、CI が英語・中国語・韓国語・スペイン語の訳を作り、その PR に足します。

訳のファイルは手で直しません。直すときは、日本語の記事を直します。

## 9. merge と公開

merge と公開は代表が行います。develop から main へのリリースで本番に出ます。書いた人が merge する作業はありません。

## 10. 公開前チェックリスト

- [ ] frontmatter の必須項目がすべて入っている
- [ ] description が空ではない
- [ ] category が `ai`、`engineering`、`founder`、`lab` のどれか
- [ ] 出典が最後の「## 参考資料」にリンクの箇条書きで入っている
- [ ] 本文に営業の誘い文句がない
- [ ] ISMS を「取得済み」と書いていない
- [ ] `npm run blog:check` が通った
- [ ] `npm run polish -- prepare` と `check` を行った
- [ ] `npm run build` が通った
- [ ] PR の宛先が develop になっている
- [ ] 訳のファイルを手で直していない
