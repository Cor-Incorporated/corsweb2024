# cor-jp.com のブログ記事を新しく書いて、公開の準備をするまで

対象: 新しく入ったスタッフ（エンジニアでなくてかまいません）
範囲: 記事を書き始めてから、代表に公開を頼める状態にするまで
この手順でやらないこと: merge と公開。これは代表が行います

## 全体の流れ

1. 記事を書く（管理画面を使う）
2. 記事の決まりごとを守る
3. 保存して PR（公開前の確認依頼）を作る
4. 3 つの検査を通す
5. 翻訳は CI が自動で足す。待つだけ
6. 代表に merge を依頼する

## 1. 記事を書く

### 1-1. 書く場所

管理画面（Sveltia CMS）で書きます。

- URL: https://cor-jp-cms-admin.web.app/

エンジニアは管理画面を使わず、ファイル `src/content/blog/ja/<記事名>.md` を直接作ってもかまいません。この手順書では、以後「記事」はそのファイルのことも指します。

### 1-2. 記事の項目（frontmatter）

記事の先頭には、次の項目があります。管理画面では入力欄になっています。

| 項目 | 必須 | 書くこと |
|---|---|---|
| title | 必須 | 記事の題 |
| description | 必須 | 記事の説明。空にしない |
| pubDate | 必須 | 公開日 |
| category | 必須 | `ai`、`engineering`、`founder`、`lab` のどれか 1 つ |
| tags | 必須 | 記事のタグ |
| author | 必須 | `"Terisuke"` と書く |
| lang | 必須 | `"ja"` と書く |
| summary | 任意 | 2〜3 文。記事の上に「この記事の要点」として出る |
| image | 任意 | 記事の画像 |

ファイルを直接作る場合の書き方の例です。

```yaml
---
title: "記事の題"
description: "記事の説明。空にしない"
pubDate: 2026-10-30
category: "ai"
tags: ["タグ1", "タグ2"]
author: "Terisuke"
lang: "ja"
summary: "この記事で分かることを 2〜3 文で書く。"
---
```

category は上の 4 つ以外を書けません。frontmatter が間違っていると、あとの `npm run build` で落ちます。

### 1-3. 本文の決まり

- 出典は本文の最後に「## 参考資料」という見出しを置き、その下にリンクの箇条書きで並べます
- 本文に営業の誘い文句を入れません
- ISMS について書くときは、次の範囲までにします
  - 書いてよいこと: 「2026年10月に ISO/IEC 27001 の第2段階審査を終え、2026年12月ごろの認証登録を見込んでいる」
  - 書かないこと: 「取得済み」

「## 参考資料」の書き方の例です。

```markdown
## 参考資料

- https://example.com/source-1
- https://example.com/source-2
```

## 2. 保存して PR を作る

管理画面で保存すると、develop 向けの PR が自動でできます。自分で PR を作る作業はありません。

エンジニアがファイルを直接作った場合は、develop に PR を出します。

PR の URL はこのあと代表に伝えるので控えておきます。

## 3. 検査を通す

次の 3 つは、ターミナルで実行するコマンドです。手元で実行できない場合は、エンジニアに「この 3 つを実行してほしい」と頼みます。`<記事名>` は自分の記事のファイル名に置き換えます。

### 3-1. 文言の検査

```bash
npm run blog:check -- src/content/blog/ja/<記事名>.md
```

指摘が出たら、その文言を直して、もう一度実行します。

### 3-2. 推敲の検査

まず、推敲の準備をします。

```bash
npm run polish -- prepare --file src/content/blog/ja/<記事名>.md
```

結果を見て記事を書き直したら、書き直した最終稿を指定して検査します。

```bash
npm run polish -- check --file src/content/blog/ja/<記事名>.md --final <最終稿のファイル>
```

### 3-3. ビルドの検査

```bash
npm run build
```

これが通ることを確かめます。frontmatter が間違っていると、ここで落ちます。落ちたら「1-2. 記事の項目」の見直しが必要です。

## 4. 翻訳を待つ

PR を develop に出すと、CI が英語・中国語・韓国語・スペイン語の訳を作り、PR に足します。自分で翻訳する作業はありません。

訳のファイルは手で直しません。訳が気になる場合は、日本語の記事のほうを直します。

## 5. 代表に merge を依頼する

次がそろったら、代表に PR の URL を伝えて merge を依頼します。

- 「3. 検査を通す」の 3 つが通っている
- 翻訳が PR に足されている

merge と公開は代表が行います。develop から main へのリリースで本番に出ます。

## 最後の確認リスト

- [ ] title と description が入っている（description は空ではない）
- [ ] category が `ai`、`engineering`、`founder`、`lab` のどれか
- [ ] author が `"Terisuke"`、lang が `"ja"`
- [ ] 出典が最後の「## 参考資料」にリンクの箇条書きで置いてある
- [ ] 本文に営業の誘い文句がない
- [ ] ISMS を「取得済み」と書いていない
- [ ] `npm run blog:check` が通った
- [ ] `npm run polish -- check` が通った
- [ ] `npm run build` が通った
- [ ] 翻訳が PR に足された
- [ ] 代表に PR の URL を伝えた

## 問題が起きたら

| 起きたこと | 見るところ |
|---|---|
| `npm run build` が落ちる | frontmatter。項目の抜け、空の description、4 つ以外の category |
| `npm run blog:check` で指摘が出る | 指摘された文言を直して再実行 |
| 訳のファイルを直したくなった | 訳は手で直さない。日本語の記事を直す |
| 公開したい | 自分では merge しない。代表に依頼する |
