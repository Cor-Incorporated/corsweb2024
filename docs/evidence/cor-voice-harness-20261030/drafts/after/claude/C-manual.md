# cor-jp.com のブログ記事を新しく書いて、公開の準備をするまで

この手順書は新しく入ったスタッフ向けです。記事を書いてから、代表が公開できる状態にするまでを扱います。merge と公開そのものは代表が行うので、この手順書には含めません。

## 記事に入れる項目

記事の先頭には次の項目（frontmatter）を書きます。

| 項目 | 書くもの |
|---|---|
| title | 記事の題 |
| description | 記事の説明。空にしません |
| pubDate | 公開日 |
| category | ai、engineering、founder、lab のどれか |
| tags | 記事のタグ |
| author | "Terisuke" |
| lang | "ja" |

任意で、次の 2 つを付けられます。

- summary。2〜3 文で書きます。記事の上の「この記事の要点」に出ます。
- image。記事の画像です。

## 書くときの決まり

- 出典は最後の「## 参考資料」にリンクの箇条書きで置きます。
- 本文に営業の誘い文句を入れません。
- ISMS について書くときは「2026年10月に ISO/IEC 27001 の第2段階審査を終え、2026年12月ごろの認証登録を見込んでいる」までにします。「取得済み」とは書きません。

## 手順 1. 記事を書く

記事は管理画面（Sveltia CMS）で書きます。

1. 管理画面 https://cor-jp-cms-admin.web.app/ を開きます。
2. 「記事に入れる項目」の表にある項目を埋め、本文を書きます。
3. 保存します。保存すると、develop 向けの PR ができます。

エンジニアは管理画面を使わずに `src/content/blog/ja/<記事名>.md` を直接作ってもかまいません。この場合は、手順 3 で PR を develop に出します。

## 手順 2. 文言と推敲を検査する

`<記事名>` は、記事のファイル名に置き換えます。

1. 文言を検査します。

   ```bash
   npm run blog:check -- src/content/blog/ja/<記事名>.md
   ```

2. 推敲の検査をします。

   ```bash
   npm run polish -- prepare --file src/content/blog/ja/<記事名>.md
   ```

3. 検査の結果を見て記事を書き直したら、元の記事と最終稿を渡してもう一度検査します。

   ```bash
   npm run polish -- check --file src/content/blog/ja/<記事名>.md --final <最終稿>
   ```

4. build が通ることを確かめます。frontmatter が間違っていると、ここで落ちます。落ちたら「記事に入れる項目」の表と見比べて直し、もう一度実行します。

   ```bash
   npm run build
   ```

## 手順 3. PR を develop に出して、訳を待つ

1. 管理画面で保存した記事は、保存した時点で develop 向けの PR ができています。記事のファイルを直接作った場合は、PR を develop に出します。
2. PR を develop に出すと、英語・中国語・韓国語・スペイン語の訳を CI が作って PR に足します。訳ができるまで待ちます。
3. 訳のファイルは手で直しません。

## 手順 4. 公開を待つ

merge と公開は代表が行います。本番に出るのは、develop から main へのリリースのときです。手順 3 まで終えたら、代表の merge を待ちます。
