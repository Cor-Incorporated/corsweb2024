# ADR-0025 チャット以外の連絡の手段（営業を避けながら、本物の問い合わせを取りこぼさない）

## ステータス: Proposed (2026-10-26)

代表が下の「決めてほしいこと」を選んだら、Accepted にして、選ばなかった案を「代替案」に移す。

## 背景

- 代表の悩み（2026-10-26）: 営業の連絡を避けたいので、電話番号やお問い合わせフォームは置きたくない。でも、連絡先がチャットボットだけだと、結局問い合わせが減って困る。
- `/contact` の連絡の手段は Cloudia（AI チャット）だけ。2026-09-13 に電話とフォームを取り下げ、Cloudia が落ちたときに手段が無くなるリスクを受容した（ADR-0005 の 2026-09-13 改訂、ADR-0013）。その撤回条件を発動するための監視は、まだ設定されていない（#322）。
- Cloudia（Pages）が配信されないとき、利用者は Firebase の「AIチャットを準備しています」のページで止まり、ほかの手段を案内されない。Pages と Firebase の両方が落ちると、contact-edge の Worker は `/contact/` へ 302 で戻し、その CTA がまたチャットを指す（#352 の行き止まり）。
- 一方、連絡先はすでに公開している。`company@cor-jp.com` はプライバシーポリシーと特定商取引法の表記に、電話番号は特定商取引法の表記に載っている。調べる気のある営業は、いまでもここにたどり着ける。
- 社内のレビュー（2026-08）では、AI チャットが入口の中心だと、AI に慣れていない会社には心理的なハードルがあり、「通常のフォーム」「打ち合わせの予約」「AI と相談内容を整理する」から選べるのが理想だ、という意見が出ていた。電話は、かかってくるもののほとんどが営業だったので取り下げた（社内の打ち合わせ、2026-09）。代表は電話を受けず、日時を決めて Google Meet で話している。
- SSGFORM のフォームの送信先が、公開のリポジトリ（`ContactForm.astro`）に残っていて、ページに出していなくても外から送れる。2026-10 に SSGFORM 経由の営業の送信が届いている（どのフォームからかは未確認）。
- 会社紹介の資料は申し込みなしで見られる形でブログの CTA と About にすでに出ているが、`/contact` と Cloudia には出ていない。
- チャットの開始数・途中でやめた数・送られた数は、サイトの側では数えていない（#252）。本番の D1 と受信箱には集計に使えるものがあるが、読むには代表の承認が要る。
- 調べた案と一次資料は `docs/contact-channels-research-2026-10.md` にまとめた。判断の要らないチャットの UX は #425 と Cor-Incorporated/cloudia#33 で PR を出した（どちらも未マージ、代表の OK 待ち）。

## 決定（推し案）

3 段で足す。AI チャットを「必須の入口」に見せない、という社内のレビューの意見に、フォームを `/contact` に置かずに応える組み合わせにした。

### 1. いま足す: B「AI と話さずに伝言だけ残す」と I「資料を見る」

- I: `/contact` の Cloudia の案内の横と、Cloudia の最初の画面に、会社紹介の資料（`COMPANY_DECK_URL`、申し込みなしで見られる）へのリンクを置き、クリックを数える。連絡先を集めないので、営業の窓口にはならない。資料を公開してよいかは代表が決める。

- Cloudia の最初の画面（目的の選択肢の下）と、会話の途中のどこからでも、「AI と話さずに伝言だけ残す」を選べるようにする。
- 入力は今の引き継ぎと同じ項目（目的、お名前、メールアドレス、会社名（任意）、ご用件）。送り先も今と同じ `/api/contact/submit`。LLM を通らない（ADR-0005 の「LLM 非経由」のまま）。なお、いまの本番は送信の内容を暗号化して D1 に 90 日保存してから通知している（`storage.ts` の `createSubmission`）ので、ADR-0005 の「PII はメールのみ」は実装と合っていない。`source` で伝言と会話を分ける。
- ボット対策に Turnstile を入れる（#280）。**順番を守る**: 先に Cloudia（と障害時のページ）にウィジェットを置いて本番に出し、その後で Worker に `TURNSTILE_SECRET` を設定する。Worker は秘密情報があるとトークンの無い送信をすべて 400 で断るので、逆の順だと、いまの会話の引き継ぎを含めて、すべての問い合わせが届かなくなる（`security.ts` の `verifyTurnstile`）。
- 営業らしさの振り分けを先に入れる（Cor-Incorporated/cloudia#17 の 3 段階: すぐ通知 / 日次のまとめ / 隔離。自動では捨てない）。伝言は AI の会話を経ないので、最初はルール（定型の営業文句、送信元のドメイン、同じ内容の連投など）で判定する。伝言の本文を AI に読ませて判定するかは、#382 の後に決める。
- Cloudia（Pages）が配信されていないときに出る Firebase の `/contact/chat/` のページ（いまは「AIチャットを準備しています」だけ）に、同じ伝言の入口を出す。#322 の合成監視が見ている文言（「AIチャットを準備しています」）は残す。
- #352（Pages と Firebase の両方が落ちたときに、contact-edge が `/contact/` へ戻す）は、このページだけでは閉じない。contact-edge が戻すときに `/contact/?chat=unavailable` のように状態を付け、`/contact` がそのときチャットの CTA を「時間をおいて」の案内に替える。Firebase も落ちていれば `/contact` 自体が出ないので、そこまでは扱わない。
- `/contact` のページ自体にはフォームも電話番号もメールアドレスも出さない（ADR-0005 の改訂と ADR-0021 のガードはそのまま）。

### 2. 運用はいまから、実装は測ってから: A 日程調整

- まずは実装せず、担当者が返信のメールで予約のリンクと Google Meet の入り方を送る運用から始める（営業の目に触れない）。代表の今の運用（日時を決めて Meet で話す）と同じなので、すぐに始められる。
- B の後の 2 か月の数字を見て、返信から打ち合わせまでの往復が負担になっていれば、Cloudia で genuine と判定され、連絡先の入力まで進んだ人にだけ、予約のリンクを出す。この判定とリンクの発行はサーバー（Worker）で行い、Cloudia の SPA にリンクを埋め込まない（ブラウザの値で判定すると、誰でもリンクを出せてしまう）。
- 道具は、cor-jp.com の Google Workspace が予約者のメール確認を使えるエディションなら Google カレンダーの予約スケジュール（新しい委託先が増えない）。使えなければ、1 回限りのリンクを出せるもの（TimeRex のワンタイム URL、Calendly の single-use link）を比べ直す。

### 3. あわせて検討する: F「広告メールお断り」の表記

- すでに公開している `company@cor-jp.com` の直前か直後に「広告宣伝メールの送信はお断りします」と書くと、「アドレスを公開している事業者には同意なしに送れる」という例外が外れる（特定電子メール法 施行規則第 3 条）。同意を得た人、名刺などでアドレスを知らされた人、取引のある人からは、引き続き送れる。費用はかからない。
- ただし `/privacy` と特商法のページは法務の文書なので、弁護士の確認を通してから変える（#382 と同じ流れ）。

### いまは採らない

- C 有料の診断を入口にする: 営業はほぼ止まるが、迷っている本物の相談者も減る。サービスのページで有料の診断を売るかは、作業 C（ADR-0024、未作成）の判断に任せる。
- D LINE 公式アカウント: 誰でも友だち追加でき、相手の私用の LINE に会社の相談が入る。
- E 050 の AI 電話受付: 番号を出せば営業電話が来る。ADR-0011 の公開の条件（着信・転送・録音の案内・個人情報・弁護士の確認）も終わっていない。B と A で足りなければ、もう一度検討する。
- F' `/contact` にメールアドレスを出す: 人の営業は止まらない。「広告メールお断り」で歯止めをつけても、仕分けの手間は残る。
- G 取材専用の窓口: Cloudia の目的「取材・登壇・その他」と B で足りる。
- SNS の DM: 営業がよく使う経路で、目的と逆を向く。

## 理由

- B は新しい委託先を増やさず、集める個人情報も今の引き継ぎと同じ項目で、費用もかからない。AI と話したくない人と、Cloudia の調子が悪いときの両方を受けられる。営業も入ってくるが、振り分けで担当者の目に触れる量を抑えられる。
- 営業を減らす効き目が測られている手段は見つからなかった（「営業お断り」の表示も、ハニーポットも、二次資料の数字しかない）。だから、効き目の分からないものを一度に足すより、B を入れて数えてから A に進むほうが、何が効いたかを確かめられる。
- 電話番号とメールアドレスはすでに公開しているので、「`/contact` に出さない」ことで減らせている営業は、ついでに連絡してくる分にとどまる。新しい入口の営業の来やすさも、この前提で比べた（何も公開していない状態からの増分としては比べていない）。

## 測り方と見直し

- B を入れる PR で、#252 の計測イベントのうち問い合わせの分（Cloudia を開いた、目的を選んだ、連絡先の入力まで進んだ、送った、伝言を送った）を先に入れる。
- 毎月、次を数える: 会話経由と伝言経由の送信の数、分類（genuine / sales / spam）の内訳、担当者が「本物の問い合わせ」とした数。
- 注意: いまの `/submit` は、分類（`classification`）をブラウザが送った値のまま保存している（`validate.ts`・`storage.ts`）。数える前に、Worker が会話（`contact_sessions`）の分類を使うように直す。伝言はルールでの判定をサーバーで付ける。
- 注意: D1 の期限切れの削除が外部キーで失敗し、行が消えずに残っている可能性がある（#430）。数える前に直す。
- 見直しは ADR-0005 の定期見直しと同じ 2026-12-13 に行う。そのとき、次のどちらかなら案を変える（数字は代表が決める）。
  - 伝言経由の営業が多く、日次のまとめを見る手間が回らない → Turnstile の設定を強める、伝言の入口を目的の選択の後ろへ下げる
  - 本物の問い合わせが増えない → A を前倒しする、E を検討し直す

## 影響

- Cloudia（Cor-Incorporated/cloudia）: 伝言の入口、Turnstile のウィジェット、計測イベント。
- corsweb: `/contact` の Cloudia の案内に資料のリンク（I）。`/contact/chat/` の代わりのページに伝言の入口（`HandoffForm.astro` の入力欄と、`ContactChat.astro` の送信の処理を流用できる。目的の欄は足す）。contact-edge が `/contact/` へ戻すときの状態の受け渡し（#352）。`workers/contact-chat` の `source` の許可、ルールでの振り分け、分類をサーバー側で決めること、`TURNSTILE_SECRET` の設定（ウィジェットの後）。`src/config/contact-guards.ts` の B-3（自己ループの禁止）と C（未配信の判定）に、伝言の入口を足しても通ることをテストで固定する。
- ADR-0005・ADR-0012・ADR-0013: Cloudia の障害時に最小限の伝言の入口を戻すので、2026-09-13 に撤回した fallback（ADR-0005 の §6、ADR-0012 と ADR-0013 の fallback フォーム）を一部改める。`/contact` には出さない点と、問い合わせが contact-chat に集まる点（ADR-0013 の一極集中）は変えない。
- プライバシーポリシー: B と A は今の Cloudia と同じ項目を新しい経路で集める。#382 の第10項と L8（同意の文言）に響く。ポリシーはこの ADR では直さない。
- 本番の Worker のデプロイと、Turnstile の秘密情報の設定は、代表が行う（手順は B を入れる PR に書く）。

## 決めてほしいこと（代表）

1. 推し案（B と I をいま足す、A は返信の運用から始めて実装は測ってから、F は弁護士の確認の後）でよいか。
2. B の伝言の入口を、Cloudia の最初の画面にも出すか、会話の途中と障害時のページだけにするか（社内のレビューの意見に沿うなら、最初の画面にも出す）。
3. 本番のデータを読んでよいか。読むなら、どれか（調査の文書の 2 節: D1 の集計 2 本、Cloudflare Web Analytics、`cloudia@cor-jp.com` の受信箱の件数、2026-09-13 より前のフォームの受信の件数）。
4. cor-jp.com の Google Workspace のエディション（A の道具が決まる）。
5. 会社紹介の資料（`COMPANY_DECK_URL`）を `/contact` と Cloudia に出してよいか。
6. SSGFORM の管理画面で、ContactForm の送信先を止めるか（外からの直接の送信は止まるが、Cloudia を止めたときの非常口のフォームも使えなくなる）。止めないなら、送信先の URL をリポジトリから外す方法（環境変数に移す）を検討する。
