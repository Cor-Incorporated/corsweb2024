# cor-voice

Cor.株式会社と Grift の公開文を、代表・寺田康佑（terisuke）の書き方に寄せるための調整です。
推敲の規則そのものは yomiyasu スキル（`.claude/skills/yomiyasu/`）に従います。このスキルはその上に「どの場面でどの文体にするか」「本人の書き方の何を残し、何を持ち込まないか」「読みやすさ・見られやすさ」「サイトで書いてはいけないこと」を足します。

食い違ったときは、次の順で優先します。

1. ADR の表現ルール（cor-jp.com は `docs/adr/`、griftai.org は `planning/` と CLAUDE.md が指す ADR）
2. yomiyasu の「意味の保持」と「情報の不増補」（主張、比重、言い切りの強さ、文の働き、数値、固有名詞を変えない。根拠のない事実を足さない）
3. このスキルの文体の指定（読みやすさ節はさらに下位）

書き方の根拠は本人の公開記事 26 本（note 22 本、Qiita 4 本）と、Claude との会話での本人の発言、および 2026-10-28 の高エンゲージ調査です。調べた範囲と、AI の下書きらしい記事を手本から外した理由は `references/evidence.md` にあります。

## 1. 進め方

1. 文章の場面を下の「2. 場面ごとの文体」から 1 つ選ぶ。選べないときは、ページの持ち主（会社か、代表個人か）と読み手で決める。
2. yomiyasu の文書の種類を決める。LP やサービスの紹介文は promo、コラムと解説記事は article、操作の説明は manual、規約やポリシーは formal、架空の物語は essay。読者は経営者・営業・採用担当向けなら informed、エンジニア向けの技術記事なら expert にする。
3. yomiyasu の Step 1〜5 で推敲する。検査（`yomiyasu_check.py run` と `verify`）は省かない。
4. 3 の結果に、このスキルの「3. 本人の書き方で残すもの」「4. 持ち込まないもの」「5. 読みやすさ・見られやすさ」を当てる。ここでも意味と数値は変えない。
5. 推敲後の全文を一度通しで読み、トーンのちぐはぐ（例: です・ますの技術告知に方言語尾だけ混ざる）があれば直す。媒体例外は「入れてよい」であり「入れるべき」ではない。
6. 「6. サイトの表現ルール」「6A. 共通メッセージ・状態・語彙」と、リポジトリの検査（下の「7. 検査」）を通す。

既存の文章を直すときは、文体を寄せるために事実や主張を足さない。本人らしい問いかけや結びを足したくなっても、原文と資料にない中身は書かない。新しく書くときも、数値、実績、社名、人の発言は資料にあるものだけを使う。

## 2. 場面ごとの文体

### 会社として書く文章

cor-jp.com のページ、サービス紹介、会社概要、FAQ、ブログの解説記事（ai・engineering カテゴリの多く）、griftai.org の LP・料金・FAQ・コラムが当たる。社内向けの手順書と説明もここに入る。

- です・ます調。主語は「Cor.株式会社では」「Cor.」「Grift は」。会社の文章で「僕」「私」は使わない。
- 1 文は短め（平均 30 字前後）。1 段落は 1〜3 文。
- 読み手が次に何をすればよいかを、最後に 1 か所だけ書く。
- 手順書は、読み手が上から順にすることを番号つきの手順で書く。項目を太字のラベルとコロンで始めない（4 章）。資料に無い手順、ツール、担当者を足さない。

### 代表の名前で書く文章

founder カテゴリの記事、note や Qiita からの転載、代表のあいさつが当たる。

- 自称は「僕」。2026 年の記事と同じく、です・ます調を基本に、短い言い切りを挟んでよい（「7倍になった。」「それは、おかしい。」）。
- 1 文 1 段落の短い区切りを使ってよい。
- 経歴は細部で語るか、1 行で済ませる（「僕は、もともとプログラマーじゃない。音楽をやっていた。営業もやった。」）。

### 技術の記事

lab・engineering カテゴリの検証記事、Grift CLI の使い方、Qiita 型の記事が当たる。

- です・ます調。手順、表、箇条書きを使ってよい（yomiyasu の manual と article の規則どおり）。
- 数字には定義、版、期間、分子と分母を付ける（「`0.2664` ではなく、`73 / 274` と読む」）。
- 何が言えて、何が言えないかを分けて書く。

代表の名前で書く文章と技術の記事は、1 文の平均を本人の 2026 年の記事の幅（17.8〜27.2 字）に寄せる。2026-10-30 に 4 本を `cor-voice-gate/scripts/cor_voice_lint.py stats` で測った値で、測り方は `references/evidence.md` にある。同じ日に比べた AI の下書きは、記事と返信メールで 28.7〜33.4 字だった。平均が 30 字を超えたら長い文から見直す。文を分けるのは、つなぎ言葉で前後の関係を残せるときだけにする（yomiyasu Step 2 の 13）。

### メールと返信（顧客、候補者、取引先）

問い合わせへの返信、候補者や取引先へのメール、フォームの回答が当たる。代表の名前で送るものも、会社としての返事なのでこの場面にする。

- です・ます調。名乗りと署名は会社と名前（「Cor.株式会社の寺田です」）。本文は自称なしで書ける形を先に考え、要るときは「私」にする。「僕」は代表個人の発信だけに使う。
- 相手の問いへの答えを、最初の 5 行のうちに書く。できないことは先に書く（3 章「出さないもの、言えないことを先に書く」）。
- 金額、日程、期限、約束は、依頼と資料にあるものだけを書く。資料に無い日程はこちらで作らず、相手に候補を聞く。
- 1 文は短く、1 段落は 1〜3 文。宛名、あいさつ、結び、署名は残してよい（yomiyasu の mail の規則）。原文に無い「させていただく」は作らない。
- 根拠: 本人の会話の特徴（です・ます調で短い、理由を聞く、決めるときは短い。`references/evidence.md`）。本人が書いたメールの実例は、まだ evidence.md に入っていない。

### Grift のストーリー（架空の物語）

griftai.org の `/column/story-*` が当たる。

- 原文の文体（語りの常体・敬体）を保つ。架空の物語であることの表示は消さない。
- 登場人物の気持ちや比喩は yomiyasu の essay の規則どおり書き手の表現として残す。

## 3. 本人の書き方で残すもの

原文にこれらがあれば残し、言い換えで消さない。新しく書くときは、資料の範囲で使ってよい。

- 問いを重ねて、分からないことを具体にする。「でも、何を作ったのか。」「一人で作ったのか。チームで触ったのか。」
- 出さないもの、言えないことを先に書く。「Grift CLIは、技量の総合点を出しません。」Grift の公開説明では、§5 の読み手に向けた説明を優先する。
- 否定してから言い直す。「期間は必要です。ただ、期間をそのまま技量へ読み替えるのは違う。」
- 数字は出典、期間、定義と一緒に書く。「8月1日から23日までで2,907件。」「特に指定がなければ1人月を160人時…として扱っています。」
- たとえは 1 つだけ、理由と一緒に使う（健康診断の血圧のたとえ）。
- 結びは控えめにし、判断を読み手に返す。「判断するのは人間です。」
- うまくいかなかったことも書く。「効かなかった結果も、基準を下げずに公開する。」
- 講演、事例、記事は、現場で実際に起きたことを主役にする。作った例は補いに使う。裏付けのある範囲の話は残し、全部を裏付けられないことを理由に丸ごと外さない。
- よく使う語は「確かめる」「検算」「事実」「違和感」「実測」。硬い言い方より、ふだんの言い方を選ぶ（代表の指摘で「試行」を「テストしてみる」に改めた）。

## 4. 持ち込まないもの

本人の公開記事にない、または AI の下書きで増えた型です。原文にあれば、yomiyasu の規則で直す。

- 大げさな決まり文句（「天元突破」「断言しよう」「未来を変える力」「〜と言っても過言ではない」）。
- 「〜とは何者か？」「〜とは？」の見出し、太字のラベルとコロンで始める箇条書き、ダッシュ（——、――）、「…」の多用。
- 感嘆符。2026 年の記事には 1 つもない。会社の文章でも使わない（引用と製品名は除く。代表個人の X の例外は 5 を参照）。
- 方言の語尾（「〜んよね」「〜やん」）と「（笑）」。公開記事にはほぼなく、下書きでだけ増えていた。代表の名前で書く文章でも新しく足さない（代表個人の X の例外は 5 を参照）。
- 会社の文章での「。。。」「笑」などのくだけた記号。代表の名前で書く文章で原文にあれば残す。
- 一つの文章の中で「僕」と「私」を混ぜること。
- 依頼と資料に無い方針や提供の状態を、言い切りで足すこと（「〜をおすすめしています」「〜にも対応しています」）。2026-10-30 のツールの比較で、AI の下書きに出た（例: 返信メールの「〜をおすすめしています」）。足したいときは本文の外の「確かめたい点」に書く。
- 依頼と資料にある固有の言葉（「TEP」「テスト導入（PoC）」、規範や機能の名前）を、似た一般の言葉に言い換えること（「TEP に沿わない」を「考え方に沿わない」にするなど）。

## 5. 読みやすさ・見られやすさ

この節は、ADR、yomiyasu、3 の残すもの、4 の持ち込まないものと衝突したら必ず負けます。足すのは順序・長さ・配置だけです。新しい主張・数字・感嘆符は足しません（下の X の例外を除く）。数値の目安はすべて仮です（長文の冒頭約 200 字、Fast の約 400 字など）。

- 実測の記事は、測った条件と日付をタイトル直下か最初の段落に置く。更新したなら更新日も置く。
- 長文は、最初の要点を本文の最初の約 200 字以内に出す（仮）。出せないときは、短い結論の節を先に置いてよい。他の書き手の見出し語（「まず30秒で」など）はまねない。
- X で数値の差分（バージョン更新、ベンチ比較）を伝えるときは、1 行目に対象を書き、その下に 2〜5 行の箇条書きを置く（仮）。1 行に数値は 1 つ。感嘆符と絵文字は 4 のとおり（代表個人の X は下の例外を参照）。
- X の記事告知は「書きました」だけにしない。記事タイトルか要旨を 1〜2 行入れてからリンクを置く。
- 限界、失敗、適用範囲は削らない。実測なら結果のすぐ後、長文なら末尾近くに 1 段落でまとめる。これは 3 の「うまくいかなかったことも書く」の再掲で、新しい決まりではありません。

媒体の例外:

- 代表個人の X（@cor_terisuke）に限り、「！」「www」「やねん」「やん」「んよね」、絵文字、「（笑）」「笑」、およびそれに準ずる口語や感嘆の連続を**持ち込んでもよい（任意）**。用途はネタ・雑談など面白みを足すときだけ。通常の告知では使わない。チェックリストとして挿入しない。原文に自然にあれば残してよい。
- 技術告知・脆弱性・ISMS・製品／記事告知など落ち着いたトーンの投稿では、例外があっても方言語尾を足さない。全文を通して読んで違和感があれば標準語に直す（cor-voice-gate の whole-post tone check）。
- note、会社の文章、LinkedIn、Qiita、サイト本文では、従来どおり 4 のとおり持ち込まない。
- X でも、会社のアカウントや会社のトーンで書く投稿には当てない。
- 例外は口調だけです。事実、数字、6 章以降のサイトの表現ルール（ISMS、Grift の説明など）はそのまま守る。

この節に入れないもの:

- 改行密度、平均文長、1 文 1 段落率の目標値（調べた範囲で差がなかったため）。
- 番号付き見出しのテンプレート（「1. はじめに」など）。
- 強い呼びかけの CTA（「スキ・フォローを」「次はあなたの番だ」など）。
- 「〜とは？」の見出し。

## 6. サイトの表現ルール

詳しい決まりは各リポジトリの ADR と CLAUDE.md にあります。推敲で取り違えやすいものだけを挙げます。

- 社名は「Cor.株式会社」。ほかの表記（Cor.inc、Cor株式会社、読みがな付き）を新しく書かない。
- Grift はエンジニアの git 履歴から確かめられる事実を取り出す自社プロダクト（OSS の Grift CLI、MIT ライセンス）と、紹介会社・SES の営業と自社開発企業の採用担当に向けたテスト導入（PoC）。見積もりのツールとは書かない。点数、順位、合否は出さない。採用担当向けの文でも、選考の合否や候補者の順位に使うとは書かない（Grift の利用規範）。2026 年 8 月の記事は Grift を「参考見積もり」の文脈で説明しているので、説明は写さない。
- Grift の公開文は、最初の 1 文で読み手が何を知れるかを平易に書く。人材紹介会社・SES の営業、自社開発企業の採用担当、エンジニア本人それぞれの使い方を書く。
- 英語のキー名や数字は本文の主役にせず、根拠として後ろか注に回す。専門の言葉は初めて出たところで一言説明する。点数・順位・合否・推薦をしないことは、否定の列挙にせず「何を出すか」で伝える。日本語と英語の両方を用意し、英語は直訳にしない。
- Grift を性格診断と呼ばず、タイプ名を付けない。MBTI は「MBTI のような型ではなく」という対比でだけ使い、経歴書の自己申告や年数・人月だけでは仕事の仕方が分からないという読み手の困りごとに結びつける。MBTI に触れるときは、Myers & Briggs Foundation の商標であり、提携していない旨を添える。
- 紹介会社向けの取り組みは「テスト導入（PoC）」、CTA は「自社でテストしてみる」。「試行」は使わない。
- 事業の柱は 5 本（Grift、ローカル LLM・セキュア AI、ハードウェア AI、AI 受託開発・導入支援、教育・コミュニティ）。順番と呼び方は ADR-0022 のとおり。
- ISMS は「2026年10月に ISO/IEC 27001 の第2段階審査を終え、2026年12月ごろの認証登録を見込んでいる」まで。「取得済み」「認証取得」と書かない。審査機関の名前を書かない。
- 信頼境界・エッジ・ゼロトラスト・クラウド／ローカルの話では、次を守る（2026-10-29 note C 外部レビュー→一連投稿ゲート）。「同じクラスタ＝同じ信頼境界」と断定しない（無条件参加で境界が曖昧になる、と書く。物理／NW位置だけで信頼しない）。エッジの価値を「止まらないこと」だけにしない（可用性・リアルタイム・**安全に停止できること**）。クラウドを「事業者が境界を引いてくれていた」と書かない（共同責任。ローカル化で物理・運用管理まで自社責任が広がる）。「売っているのは速さではない」だけの否定見出しにしない（性能要件を満たすだけでなく、安全に運用できる構成まで。推論 R&D の強みは否定しない）。
- 「売っているのは速さではない」は、**「速度だけでは、業務に使えるかは決まらない」**に言い換える（2026-10-29 レビュー §4.1、続稿① n083decbc281b 境界・安全停止で寺田判断により確定）。速度が必要条件であることは否定しない。
- 境界・停止設計の記事（続稿① n083decbc281b を含む）では、エッジの価値を「可用性・リアルタイム応答・安全に停止できること」の三つ並びで書き、どれか一つに縮めない。Cor. の選択（この条件で分離を選ぶ方針）と一般原則を分け、方針を実装済み・検証済みと書かない。
- デモやスイカ割りなどの実演はシミュレーション検証まで。実機での断定は書かない。
- 名前を出してよい連携先はエンジニアカフェ（Engineer Cafe）だけ。「福岡を代表する企業100選」は書いてよい。
- 言い切りの保証（「確実に」「必ず」「絶対」）、根拠のない最上級、作った顧客名や声は書かない。社内の計測値や倍率は、条件を説明したページへのリンクがあるときだけ。
- CTA で「無料」を主な誘い文句にしない。価格を書かない（Grift の料金は個別案内）。
- 公表の確認が取れていない予定（大会への登壇、契約の内容など）は書かない。
- griftai.org の URL を cor-jp.com のコードに直接書かない（`PUBLIC_GRIFT_BASE_URL`）。

## 6A. 共通メッセージ・状態・語彙（2026-10-29 外部レビュー反映）

出典: `/workspace/reports/20261029_cor_voice_rewrite_review.md`（以下「レビュー」）§2.2、§2.3、§3、§4.3、§4.5、§7.1〜7.4。6 章の既存ルールに足すもので、置き換えるものではありません。新しい事実・数字・実績は足しません。

### 6A-1. 共通メッセージ（レビュー §2.2）
- 短い会社説明の軸: 「AIを動かすだけでなく、業務で使える条件まで確かめる。」
- サービス説明の軸: ローカル LLM・セキュア AI と AI システム開発を中心に、設計・実装・検証を支援する。性能だけでなく、扱う情報、アクセス権限、運用、費用を確認し、導入を進めるかどうかの判断材料を整える。
- Grift の軸: 開発記録から確認できる事実を、根拠と限界とともに整理する OSS の CLI。点数で人を並べず、経歴や仕事について具体的に話すための材料をつくる。
- 「安心」は結論ではなく設計・検証の目標として使う。「ISMS だから安心」「ローカルだから安全」「ログがあるから説明できる」と一段飛ばしにしない。
- セキュリティを強調しすぎて、実装力や性能研究を消さない。
- 5 本の柱は同じ強さの売り文句にしない。商談入口（ローカル LLM・セキュア AI、AI 受託開発・導入支援）／製品の柱（Grift CLI）／先行投資（フィジカル AI 等の研究）／信用の基盤（講師・登壇・OSS・地域）の順で説明する（レビュー §2.1。柱の呼び方と順番は ADR-0022 が優先）。

### 6A-2. 代表個人と会社の分け方（レビュー §2.3）
- note・個人 SNS は本人の声（僕、実験の熱量、失敗、判断が変わった経緯）でよい。全部を「弊社」に置き換えない。
- サービス範囲、機能、納入実績、認証の状態、料金・契約条件は会社の責任で揃える。
- 「僕のこの条件では動いた」と「Cor. が顧客環境で提供できる」は別の段落に書く。個人の体験を会社の保証へ広げない。

### 6A-3. 状態の区別（レビュー §7.1）
文ごとに、次のどの状態かを読み手が取り違えないようにします。

| 状態 | 書き方 | 書かない飛躍 |
|---|---|---|
| 方針 | この用途では分離する方針です | 分離しているので安全です |
| 実装 | この版に機能を追加しました | 実装したので運用上の問題はありません |
| 検証 | この入力・構成で、この結果を確認しました | どの環境でも動きます |
| 本番運用 | 対象・期間・運用条件を明示して利用されています | デモの公開を本番稼働と呼ぶ |
| 顧客成果 | 掲載許可と測定条件のある成果だけ | 自社実験の改善率を顧客効果に使う |
| 計画 | 開始予定・検証準備中と書く | 予定を提供中の実績欄に混ぜる |

あわせて、実機とシミュレーション、実行できることと利用許可があること、自社開発と他者の実装への検証協力を分けます。

### 6A-4. P0 語彙（レビュー 要旨、§3、§4.1〜4.5）
- **「証拠は盛れない」は使わない。** 共通コピーは「経歴の説明に、確かめられる根拠を。」。「経歴は盛れる。証拠は盛れない。」も同じく使わない。再計算できることと、入力記録が完全・真正であること、能力を測れることは別と書く（レビュー §4.5）。
- 「同じ記録なら同じ値」には、入力範囲・commit、CLI 版、定義・設定が同じという条件を添える。
- **「7倍」は指標を分ける。** 実測したのは GitHub のコントリビュート数（Issue・PR・レビュー等を含む）であり、生産性・開発速度・納品量の 7 倍ではない。タイトル・冒頭・要約・OGP が同じ指標を指すようにする。品質・手戻り・作業時間の改善率は主張しない。新しい母数や品質指標を作らない（レビュー §4.3）。
- **境界記事:** 6 章の note C 4 点に従う（同一クラスタ断定・止まらないことだけ・クラウド事業者任せ・速さの否定）。Cor. の選択（「Cor. はこの条件で分離を選ぶ」）と一般原則（「必ず別クラスタでなければ危険」）を分ける（レビュー §4.1）。
- **許可リスト記事:** 脆弱性対応と許可設定の管理を対立させない（どちらか一方で済まない）。許可リストが決めるのは通信を通してよい相手であり、誰が何の業務に使ってよいか（認証・認可）までは決まらない、と書く。到達制御だけで十分と読めないようにする。「ローカル API を呼ぶ」と「処理全体がローカルで完結する」を同義にしない（レビュー §4.2）。
- 「日本初」「最速」「唯一」「完全」「100％安全」「必ず」は強い根拠と定義がなければ使わない。「最適」「高精度」は誰のどの要件に対してかを示す（レビュー §7.2）。

### 6A-5. 数字・比較・安全性（レビュー §7.2）
- 数字には、何を数えたか、期間、分母、対象、条件、未観測を付ける。速度ならモデル・量子化・ハードウェア・実装版・入出力長・同時実行・測定方法。SNS 本文に全部詰めず、詳細資料へ分けてよい。
- 外部調査は発表年、対象、予測か実績かを書き、自社製品の効能へ読み替えない。
- オールローカル、ノーログ、AI 不使用、個人を評価しない、などの約束は、UI の既定値、送信経路、エラーログ、オプション機能まで突き合わせてから書く（Grift の「宣言と実装の突き合わせ」の横展開）。
- 他者の実装の高速化倍率を Cor. の成果として書かない（レビュー §4.16）。

### 6A-6. 記事の型（レビュー §7.4）
- 推奨の流れ: **具体的な出来事→問い→観測→判断→限界→読者への意味**。冒頭に業界統計を何段も並べず、Cor. が何にぶつかり何を変えたかを先に出す。
- 注意書きを増やすだけにしない。制約は結論の近くに必要な分だけ置く。過度な留保で主張が読めなくなったら、それも失敗とみなす。
- 「速さではない」「モデルではない」「ツールではない」を続けない。「それだけでは足りない」「この条件も必要」と言い換える。
- 一記事に一つの主な次の行動。相談導線では、初回連絡に実データ・機密文書・認証情報は不要と書く（レビュー §8.1）。
