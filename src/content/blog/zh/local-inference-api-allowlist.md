大家好，我是Cor.株式会社的寺田。今天聊的话题可能稍微有点枯燥。但是，如果在企业内部运行本地AI，这恐怕是最能产生实效的一件事。

## 本地推理API是按“在手边本机使用”的假设设计的

多数在本地运行推理的工具，首先都是以在当前手边的机器上使用为前提的。

例如在Ollama的官方文档中写道，localhost上的本地API不需要认证。此外还提到，默认情况下只监听本地（127.0.0.1），可以通过配置更改监听地址。

与其说这是一个缺陷，不如说是设计的前提。因为仅在手边本机使用的话，这样就足够了。问题往往发生在这种前提被直接搬到公司内网的时候。

## “仅限内网”并不是边界的名称

为了在内网搭建推理服务器，往往会扩大监听范围以便其他终端使用。通过防火墙来决定哪些终端可以连通。到这里为止都还是常规步骤。

需要注意的是这之后的事情。

为了测试而开放的监听端口，一直就那样留着。临时添加的白名单许可，一直就那样留着。已经不再使用的终端，其许可虽然从台账中删除了，却依然留在防火墙里。

对于没有认证机制的API来说，“能连通”几乎就意味着“能使用”。因此，残留着可能被未预期终端访问的状态本身就是一种风险。“仅限内网”这句话，只有配合实际的许可配置时才有意义。

## 比关注CVE更先要做的事

追踪漏洞信息（CVE）固然重要。但我认为，还有一件事应该更早形成规范流程：那就是终端准入与退役的顺序。

漏洞可能会在某一天集中爆发。而许可配置的偏差，却在日积月累。对于后者，如果没有规程，谁也不会察觉。

## 准入的顺序

当允许新终端使用推理API时，我们遵循以下顺序：

1. 在台账中登记终端（用途、负责人、使用期限）
2. 确认终端侧的基础配置
3. 添加到防火墙的放行许可中
4. 确认网络可达，并在台账中记录确认日期

台账在先，许可在后。这个顺序至关重要。如果只先把许可配上了，之后就无法追溯“这是谁的许可、为了什么而设”。

## 退役的顺序

移除终端时，则按相反的顺序操作：

1. 从防火墙的放行许可中删除
2. 确认已无法连通
3. 清理终端侧的凭证与配置
4. 将台账更新为“退役”，并记录日期

在这里，先删除许可至关重要。仅更新了台账而残留了许可，这是最容易出现的偏差。

## 通用检查清单

这里总结了一份不仅限于特定案例、其他公司也可以参考使用的清单：

- 推理API的监听范围是否限定在预期范围内？
- 为验证而临时放开的监听，在验证结束后是否已还原？
- 防火墙的放行许可列表是否与终端台账一致？
- 每一个放行许可在台账中是否有明确的用途、负责人和有效期限？
- 退役时是否遵循“删除许可 → 确认无法连通 → 更新台账”的顺序处理？
- 是否定期（例如每月）对放行许可列表与台账进行核对？
- 是否留存了由谁在何时增删了哪些许可的日志记录？
- 当无认证的API确实需要对外暴露时，架构上是否在前端配置了认证或访问控制？

这些事项看似都不起眼。但只要这份清单持续运转，大部分偏差都能被尽早发现。

## 我们的实践

Cor.株式会社为部署在现有设备上的全本地方案提供全程陪跑支持。在ISMS的运营体系中，我们与客户一同完成架构选型，以及权限、失效机制与日志的设计。在ISMS方面，我们已于2026年10月完成ISO/IEC 27001的第二阶段审核，预计将于2026年12月左右完成认证注册。

这次提到的白名单许可运营，正是处于“失效”与“日志”核心位置的话题。相比于速度和性能的比较，我们认为持续划清这种严谨的基础界线更具价值。

## 最后

听到“没有认证”，或许会让人感到不安。但实际上，这只是了解了工具的设计前提而已。只要明确了前提，需要守护的边界也会随之清晰。

谁的终端，从何时起，到何时为止可以访问。能够在台账与许可配置两方面都给出清晰的解释——这正是我们希望守护的底线。
