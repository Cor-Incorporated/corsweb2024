## 課題

人材紹介会社やSESの営業は、候補者を企業へ推薦するときに「なぜこの方を薦めるのか」を説明する必要があります。ところが手元にある材料は、経歴書と面談の印象がほとんどです。「Java 5年」と書かれていても、どんな変更をどう確かめながら進めてきたのか、仕事の中身までは伝わりません。

一方で、GitHubの草やコミット数のような「活動量」は、生成AIやエージェントを使えば簡単に膨らむようになりました。量の多さはもう推薦の根拠になりにくい。かといって1つのスコアにまとめると、何を・どの期間で・どの母数で測ったのかが消え、足切りの道具として使われてしまいます。推薦する側にも、推薦される側にも、「確かめられる材料」が足りていませんでした。

## アプローチ

Griftは2026年2月、受託開発の見積を支えるWebアプリとして始まりました。見積の根拠を探るうちに、いちばん確かな材料はエンジニアが積み上げてきたgit履歴そのものだと気づき、2026年8月に計測の部分をコマンドラインツールとして切り出しました。9月には旧Webアプリの提供を止め、人材紹介会社・SESの営業を支える方向へ方針を変えています。

設計では3つの約束を先に決めました。

- 点数にしない: 出すのは検査値で、判断するのは人。合成スコア・順位・合否・等級は出さず、数値には必ず分子と分母を付ける
- 毎回同じ結果: 計測にAI（LLM）を使わない。同じリポジトリ・同じバージョンなら、誰が実行しても同じ数値になる
- どこにも送らない: 手元のPCだけで動く。共有するかどうか、どのリポジトリを出すかは本人が決める

あわせて、「不在を負に読まない」「数値だけで足切りしない」「本人の同意なく他人を測らない」など7条の利用規範を定め、守らない使い方は手法の名前（TEP: Technical Evidence Pipeline）で呼ばない決まりにしました。

## 実装

Grift CLIはgit履歴だけから次のような観測を取り出します。

- 帰属の区別: 本人の独自コミット、他人の仕事、bot、生成・ベンダー成果物、fork元から引き継いだ履歴など11分類で、誰の仕事かを分ける
- テスト併修率: 本番コードの変更と同じコミットで、テストも変更している割合
- 手戻り率・磨き直し: 直近に触ったファイルのやり直しや再接触の割合（傾向の記録であり、合否には使わない）
- リポジトリの文脈: 実働日数、関わった人数と最多作成者の占有率、レビュー経由の割合など

v0.6で加わった`report-v2`では、1人のエンジニアの仕事の形を見る層が増えています。いずれも分子と分母付きで、職種や能力の判定ではありません。

- 作業領域（`surface_profile`）: test / docs / CI/CD / platform / data / observability / frontend / backend / config / 生成・ベンダー / その他の11区分で、どの領域の変更が何件あったか
- 変更リズム（`change_rhythm`）: 直近180日のうち変更を提出した日数と、提出の間隔（中央値と90パーセンタイル、2日以内に続いた割合、30日以上空いた割合）。労働時間や意欲ではありません
- 検証の形（`verification_profile`）: テストを触ったコミットの割合と、その種類（unit / integration / e2e / contract / 不明）、fixのコミットにテストが伴った割合
- 役割の4次元（`role_profile`）: domain / work_type / time / process_positionの4つだけで、1つの職種に畳みません。本人の同意が記録されたidentityがあるときだけ出します

案件側との照らし合わせも、順位をつけない形で行います。案件側は`grift project`で求める領域・検証・リズム・入力を宣言し、`grift align`が候補者の観測と軸ごとに並べます。並びは重なり（overlap）・範囲外（outside_declared_range）・0件（observed_zero）・未観測（not_observed）・要求なし（not_declared）の5通りだけで、総合点・順位・合否は計算しません。`--team`でチーム単位に見るときは、要求を満たす人数だけを出し、3名未満では個人が特定されるため集計しません。

母数が20未満のときは率を出さずに件数だけを示し、観測できなかったものは「実績なし」ではなく理由付きの「未観測」として出します。`grift verify` は保存したレポートを同じ条件で計算し直し、一致・不一致・検証不能を返すため、受け取った側が書き換えや食い違いを確かめられます。

0.9.0からは`grift actor`のMarkdownの先頭に、記録から見える仕事の進め方を短い文で書きます。変えた部分の区分、変更のペース、テストの付け方、関わり方について、件数と期間を添えて書き、続けて、この記録では見えないことを書き、面談で確かめたいことを問いの形で並べます。`grift project`は案件のリポジトリの進め方を同じ決まりで書き、人ごとの数字と関わり方は出しません。`grift align`は要求と記録の並びに、面談で確かめたいことを問いの形で添えます。文と問いは公開した[決定表](https://github.com/Cor-Incorporated/grift-cli/blob/v0.9.0/docs/trait-profile.md)で数字から選び、AIは使いません。JSONには入れないので、`grift verify`で検算できるのは、文の元になった数字のほうです。

人についての文と問いは、本人が名乗ったIDで、同意の記録があるときだけ出します。それ以外は、出していない理由を1文で書きます。複数の人をまとめて出すとき（`--all`、`--top`）は文を出しません。

手法の名前はTEP（Technical Evidence Pipeline、技術の証拠を取り出す流れ）です。gitの記録を読む、決まった規則で数える、数えた値に分母と数えられなかったものの理由を付ける、誰でも同じ手順で数え直せるようにする、という4つの段階でできています。詳しい説明はGriftのサイトの[TEPのページ](https://griftai.org/tep)にあります。

このページとgriftai.orgで使っている言い方と、CLIが出力に書く語は次のように対応します。

| サイトの言い方 | CLIの語 |
|---|---|
| 検査値 | observed value（`kind: observed`。値と単位と分母が付く） |
| テスト併修率 | test co-change |
| 手戻り率 | corrective rework |
| 磨き直し | path retouch |
| コードの新しさ | survival（`--survival`を指定したときだけ） |
| リポジトリの文脈 | context profile |
| 作業領域・変更リズム・検証の形 | surface_profile / change_rhythm / verification_profile |

0.9.0からはCLIのMarkdownも、変えた部分の区分（作業領域）、変更のペース（変更リズム）、テストの付け方（検証の形）、関わり方の4つの観点を、griftai.orgと同じ呼び名で書きます。JSONのキーは変わりません。

0.9.2では、ホストにPythonを入れずに、grift-cliのリポジトリから作ったDockerイメージで実行できるようにしました。読みたいリポジトリは履歴を全部取得し、`/repo`に渡します。`git worktree`で作った作業ツリーは使えません。

`grift update`は、実行中の環境を明示的に更新し、更新後の版を表示するように変えました。`grift update --check`はPyPIの最新版の情報を読むだけで、更新はしません。自動の更新と、ふだんの測定コマンドが版を確かめる通信はありません。

`grift contribute`は本人の同意後に提出用ファイルを手元に保存し、提出に必要な情報と提出先を表示します。自動では送りません。既定の`--door local`で作ったファイルを公開して提出する場合は、`--door public-pr`で作り直し、新しく表示された提出ID・hash・metaを使います。本人が出す公開PRでも、身元を伏せた代理PRでも、ファイルの中身は公開されます。

## 成果

2026年9月8日に、PyPIで[v0.7.2](https://pypi.org/project/grift-cli/0.7.2/)を公開しました。指標は公開されている117のリポジトリで検証し、区別できた比較と、まだ区別できていない比較の両方をGitHubで公開しています（社内での測定で、第三者による監査は受けていません）。

2026年10月25日に、サイトの文言とCLIの出力を1行ずつ突き合わせました。複数人の一覧（`actor-index`）が、注記では「順位ではない」と書きながらコミット数の多い順に並んでいたため、2026年10月26日に公開した[0.8.0](https://github.com/Cor-Incorporated/grift-cli/releases/tag/v0.8.0)で、並びをIDの辞書順に変えました。コミット数の値は残しています。経緯と、0.8系に課す5つの受入条件は[ブログ記事](https://cor-jp.com/blog/grift-no-score-no-rank-in-code/)に書きました。

2026年10月27日に公開した[0.9.0](https://github.com/Cor-Incorporated/grift-cli/releases/tag/v0.9.0)で、上に書いたレポートの先頭の文と面談の問いを加えました。あわせて、傾向の「強さ」の行と、照らし合わせの「向き」の行をMarkdownから外しました。2つのレポートを並べると、強い人・弱い人、合う人・合わない人に読めるためです。人について事実と違う数が出うる箇所も4つ直しました。

2026年10月28日に公開した[0.9.1](https://github.com/Cor-Incorporated/grift-cli/releases/tag/v0.9.1)では、0.9.0のあとに見つかった、人や案件について事実と違う数が出うる箇所を直しました。新しいコマンドはなく、点数・順位・タイプ名を出さないことも変わりません。定義の版が変わったため、0.9.0で保存したレポートと照らし合わせは、0.9.1の`grift verify`では検算できなくなります（要求だけから作った案件のレポートなどの例外は、[移行の注意](https://github.com/Cor-Incorporated/grift-cli/blob/v0.9.1/docs/migration-v091.md)にあります）。

[0.9.2](https://github.com/Cor-Incorporated/grift-cli/releases/tag/v0.9.2)では、リポジトリの文脈を示す出力に、観測した履歴で初めて活動した年と最後に活動した年、タグの頻度の分子と分母を表示するようにしました。今も活動している人にも最後の活動年が表示されるため、離脱や退職を示すものではありません。タグの頻度は「タグ数 ÷ 活動期間の日数 × 365.25」の年換算の値で、観測したリリース回数ではありません。点数・順位・合否を出さないことは変わりません。

いまは、候補者本人が手元で実行した記録をもとに推薦の理由を具体的にするテスト導入（PoC）の準備を、紹介会社さま・SES企業さまと進めています。自社開発企業の採用担当の方からも、候補者本人が共有した記録から、どんな仕事をしてきたかを確かめるテスト導入（PoC）のご相談を受け付けています。正式版についてはテスト導入の結果をふまえて2027年の提供開始を目指しています。Griftは [griftai.org](https://griftai.org) でも紹介しています。

Griftの思想は[Qiita](https://qiita.com/terisuke/items/c6bb68b3af0db3d43bb1) と [note](https://note.com/cor_instrument/n/nd58ba0955317) の記事でも紹介しています。
