## 과제

인재소개회사나 SES의 영업 담당자는 후보자를 기업에 추천할 때 "왜 이분을 추천하는지" 설명해야 합니다. 그러나 수중에 있는 재료는 이력서와 면담에서의 인상이 대부분입니다. "Java 5년"이라고 적혀 있어도, 어떤 변경을 어떻게 검증하며 진행해 왔는지, 일의 알맹이까지는 전해지지 않습니다.

한편, GitHub 잔디나 커밋 수 같은 "활동량"은 생성형 AI나 에이전트를 사용하면 쉽게 부풀릴 수 있게 되었습니다. 양이 많다는 점은 더 이상 추천의 근거가 되기 어렵습니다. 그렇다고 해서 하나의 점수로 취합해 버리면, 무엇을·어느 기간에·어떤 모수로 측정했는지가 사라져 컷오프 도구로 쓰이고 맙니다. 추천하는 쪽에도, 추천받는 쪽에도 "검증할 수 있는 재료"가 부족했습니다.

## 접근 방식

Grift는 2026년 2월, 수주 개발 견적을 지원하는 웹 앱으로 시작되었습니다. 견적의 근거를 찾는 과정에서 가장 확실한 재료는 엔지니어가 축적해 온 git 이력 그 자체임을 깨닫고, 2026년 8월에 측정 부분을 커맨드라인 툴로 분리해 냈습니다. 9월에는 기존 웹 앱 제공을 중단하고, 인재소개회사·SES의 영업을 지원하는 방향으로 방침을 전환했습니다.

설계에서는 세 가지 약속을 먼저 정했습니다.

- 점수화하지 않는다: 내놓는 것은 검사값이며, 판단하는 것은 사람. 종합 점수·순위·합불·등급은 매기지 않고, 수치에는 반드시 분자와 분모를 명시한다
- 매번 동일한 결과: 측정에 AI(LLM)를 사용하지 않는다. 같은 리포지토리·같은 버전이라면 누가 실행해도 같은 수치가 나온다
- 어디로도 전송하지 않는다: 로컬 PC에서만 동작한다. 공유할지 여부, 어떤 리포지토리를 공개할지는 본인이 결정한다

이와 함께, "부재를 부정적으로 해석하지 않는다", "수치만으로 컷오프하지 않는다", "본인 동의 없이 타인을 측정하지 않는다" 등 7개 조항의 이용 규범을 마련하여, 이를 지키지 않는 사용 방식은 기법의 명칭(TEP: Technical Evidence Pipeline)으로 부르지 않기로 규정했습니다.

## 구현

Grift CLI는 git 이력만을 바탕으로 다음과 같은 관측치를 추출합니다.

- 귀속 구분: 본인의 고유 커밋, 타인의 작업, bot, 생성·벤더 산출물, fork 원본에서 이어받은 이력 등 11가지 분류로 누구의 작업인지 구분
- 테스트 병행 수정률: 프로덕션 코드 변경과 동일한 커밋에서 테스트도 함께 변경한 비율
- 재작업률·다듬기: 직전에 수정한 파일의 재작업이나 재수정 비율(경향을 기록하는 것이며, 합불 판정에 쓰지 않음)
- 리포지토리 컨텍스트: 실가동 일수, 참여 인원수 및 최다 작성자의 점유율, 리뷰를 거친 비율 등

v0.6에서 추가된 `report-v2`에서는 엔지니어 한 사람의 작업 방식을 살펴보는 계층이 늘어났습니다. 모두 분자와 분모가 함께 제공되며, 직종이나 역량을 판정하는 것이 아닙니다.

- 작업 영역(`surface_profile`): test / docs / CI/CD / platform / data / observability / frontend / backend / config / 생성·벤더 / 기타 등 11개 구분으로, 어떤 영역의 변경이 몇 건 있었는지
- 변경 리듬(`change_rhythm`): 최근 180일 중 변경을 제출한 일수와 제출 간격(중앙값 및 90퍼센타일, 2일 이내에 이어진 비율, 30일 이상 비어 있던 비율). 노동 시간이나 의욕을 나타내는 것이 아닙니다
- 검증의 형태(`verification_profile`): 테스트를 다룬 커밋의 비율과 그 종류(unit / integration / e2e / contract / 알 수 없음), fix 커밋에 테스트가 동반된 비율
- 역할의 4차원(`role_profile`): domain / work_type / time / process_position 4가지만 사용하며, 하나의 직종으로 축약하지 않습니다. 본인의 동의가 기록된 identity가 있을 때만 출력합니다

프로젝트 요구사항과의 대조 역시 순위를 매기지 않는 방식으로 진행합니다. 프로젝트 측은 `grift project`를 통해 요구하는 영역·검증·리듬·입력을 선언하고, `grift align`가 후보자의 관측치와 축별로 나란히 비교합니다. 비교 결과는 중복(overlap)·범위 외(outside_declared_range)·0건(observed_zero)·미관측(not_observed)·요구 없음(not_declared) 5가지만 사용하며, 종합 점수·순위·합불은 계산하지 않습니다. `--team`로 팀 단위로 살펴볼 때는 요구를 충족하는 인원수만 표시하며, 3인 미만인 경우 개인이 특정되므로 집계하지 않습니다.

모수가 20 미만일 때는 비율을 계산하지 않고 건수만 표시하며, 관측되지 않은 항목은 "실적 없음"이 아니라 사유를 덧붙인 "미관측"으로 표시합니다. `grift verify` 는 저장된 리포트를 동일한 조건으로 다시 계산하여 일치·불일치·검증 불가를 반환하므로, 리포트를 수령한 쪽에서 위변조나 불일치를 확인할 수 있습니다.

기법의 명칭은 TEP(Technical Evidence Pipeline)입니다. 이 페이지와 griftai.org에서 사용하는 표현과 CLI 출력에 쓰이는 용어는 다음과 같이 대응됩니다.

| 사이트 표현 | CLI 용어 |
|---|---|
| 검사값 | observed value(`kind: observed`. 값, 단위, 분모가 함께 표시됨) |
| 테스트 병행 수정률 | test co-change |
| 재작업률 | corrective rework |
| 다듬기 | path retouch |
| 정착률 | survival(`--survival`를 지정한 경우에만) |
| 리포지토리 컨텍스트 | context profile |
| 작업 영역·변경 리듬·검증의 형태 | surface_profile / change_rhythm / verification_profile |

- 리포지토리: [github.com/Cor-Incorporated/grift-cli](https://github.com/Cor-Incorporated/grift-cli)
- 배포: PyPI "grift-cli"(`pipx install grift-cli`, Python 3.11 이상)
- 라이선스: MIT

## 성과

2026년 9월 8일, PyPI에 v0.7.2를 공개했습니다. 지표는 공개된 117개 리포지토리에서 검증했으며, 구별해 낸 비교와 아직 구별해 내지 못한 비교 모두 GitHub에 공개하고 있습니다(사내 측정 결과이며, 제3자 감사는 받지 않았습니다).

2026년 10월 25일, 사이트의 문구와 CLI 출력을 한 줄씩 대조했습니다. 복수 인원 목록(`actor-index`)이 주석에는 "순위가 아님"이라고 적혀 있으면서도 커밋 수가 많은 순으로 정렬되어 있었기 때문에, 다음 버전(0.8)에서는 정렬 방식을 ID 사전순으로 변경합니다. 커밋 수 수치는 유지합니다. 경위와 0.8 버전에 적용할 5가지 인수 조건은 [블로그 글](https://cor-jp.com/blog/grift-no-score-no-rank-in-code/)에 작성했습니다.

현재는 후보자 본인이 로컬에서 실행한 기록을 바탕으로 추천 이유를 구체화하는 시험 도입(PoC) 준비를 인재소개회사 및 SES 기업들과 함께 진행하고 있습니다. 정식 버전에 대해서는 시험 도입 결과를 바탕으로 2027년 제공 개시를 목표로 하고 있습니다. Grift는 [griftai.org](https://griftai.org)에서도 소개하고 있습니다.

Grift의 철학은 [Qiita](https://qiita.com/terisuke/items/c6bb68b3af0db3d43bb1)와 [note](https://note.com/cor_instrument/n/nd58ba0955317) 기사에서도 소개하고 있습니다.
