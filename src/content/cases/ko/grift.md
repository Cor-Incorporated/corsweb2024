## 과제

인재 소개 회사나 SES의 영업 담당자는 후보자를 기업에 추천할 때 "왜 이 분을 추천하는지"를 설명해야 합니다. 그러나 수중에 있는 자료는 이력서와 면담에서의 인상이 대부분입니다. "Java 5년"이라고 적혀 있어도 어떤 변경을 어떻게 검증하며 진행해 왔는지, 업무의 실질적인 내용까지는 전달되지 않습니다.

한편, GitHub의 잔디나 커밋 수와 같은 "활동량"은 생성형 AI나 에이전트를 사용하면 쉽게 부풀릴 수 있게 되었습니다. 양의 방대함은 이제 추천의 근거가 되기 어렵습니다. 그렇다고 해서 하나의 점수로 취합해 버리면 무엇을, 어느 기간 동안, 어떤 모수로 측정했는지가 사라져 서류 탈락의 도구로 악용되고 맙니다. 추천하는 쪽에도, 추천받는 쪽에도 "검증할 수 있는 자료"가 부족했습니다.

## 접근법

Grift는 2026년 2월, 수탁 개발 견적을 지원하는 웹 앱으로 시작되었습니다. 견적의 근거를 찾는 과정에서 가장 확실한 자료는 엔지니어가 축적해 온 git 이력 그 자체임을 깨닫고, 2026년 8월에 측정 부분을 명령줄 도구로 분리했습니다. 9월에는 기존 웹 앱의 제공을 중단하고 인재 소개 회사와 SES 영업을 지원하는 방향으로 방침을 전환했습니다.

설계 단계에서 세 가지 원칙을 먼저 정했습니다.

- 점수화하지 않는다: 출력하는 것은 검사값이며 판단은 사람이 한다. 종합 점수·순위·합격 여부·등급은 산출하지 않고, 수치에는 반드시 분자와 분모를 표기한다
- 매번 일관된 결과: 측정에 AI(LLM)를 사용하지 않는다. 동일한 저장소, 동일한 버전이라면 누가 실행하든 동일한 수치가 나온다
- 어디에도 전송하지 않는다: 사용자의 로컬 PC에서만 동작한다. 공유 여부나 어떤 저장소를 제시할지는 본인이 결정한다

이와 더불어 "부재를 부정적으로 해석하지 않는다", "수치만으로 탈락시키지 않는다", "본인의 동의 없이 타인을 측정하지 않는다" 등 7개 조항의 이용 규범을 수립하고, 이를 준수하지 않는 사용 방식은 기법의 명칭(TEP: Technical Evidence Pipeline)으로 부르지 않기로 규정했습니다.

## 구현

Grift CLI는 git 이력만을 바탕으로 다음과 같은 관측값을 추출합니다.

- 귀속 구분: 본인의 독자적 커밋, 타인의 작업, bot, 생성물·벤더 산출물, fork 원본에서 이어받은 이력 등 11가지 분류로 누구의 작업인지 구분
- 테스트 동시 수정률: 프로덕션 코드 변경과 동일한 커밋에서 테스트도 함께 변경한 비율
- 재작업률·재접촉: 최근에 작업한 파일의 재작업 및 재접촉 비율(경향을 기록하는 것이며, 합격 여부 판단에는 사용하지 않음)
- 저장소의 맥락: 실제 작업 일수, 참여 인원수 및 최다 작성자의 점유율, 코드 리뷰를 거친 비율 등

v0.6에 추가된 `report-v2`에서는 한 엔지니어의 작업 양상을 파악하는 레이어가 확장되었습니다. 모두 분자와 분모가 함께 표기되며, 직무나 능력에 대한 판정이 아닙니다.

- 작업 영역(`surface_profile`): test / docs / CI/CD / platform / data / observability / frontend / backend / config / 생성·벤더 / 기타 등 11개 구분으로, 어떤 영역의 변경이 몇 건 있었는지 표기
- 변경 리듬(`change_rhythm`): 최근 180일 중 변경 사항을 제출한 일수와 제출 간격(중앙값 및 90번째 백분위수, 2일 이내로 이어진 비율, 30일 이상 벌어진 비율). 노동 시간이나 의욕을 의미하지는 않습니다
- 검증 형태(`verification_profile`): 테스트를 수정한 커밋의 비율과 그 종류(unit / integration / e2e / contract / 불명), fix 커밋에 테스트가 수반된 비율
- 역할의 4차원(`role_profile`): domain / work_type / time / process_position의 4가지만 사용하며, 하나의 직무로 축약하지 않습니다. 본인의 동의가 기록된 identity가 존재할 때만 출력합니다

프로젝트 요구사항과의 대조 역시 순위를 매기지 않는 방식으로 진행됩니다. 프로젝트 측은 `grift project`으로 요구하는 영역·검증·리듬·입력을 선언하고, `grift align`가 후보자의 관측값과 축별로 나란히 배치합니다. 배열 상태는 중복(overlap)·범위 외(outside_declared_range)·0건(observed_zero)·미관측(not_observed)·요구 없음(not_declared)의 5가지로만 표시되며, 종합 점수·순위·합격 여부는 계산하지 않습니다. `--team`로 팀 단위로 살펴볼 때는 요구를 충족하는 인원수만 출력하며, 3인 미만일 때는 개인이 특정되므로 집계하지 않습니다.

모수가 20 미만일 때는 비율을 계산하지 않고 건수만 표시하며, 관측되지 않은 항목은 "실적 없음"이 아니라 사유를 덧붙인 "미관측"으로 출력합니다. `grift verify` 은 저장된 리포트를 동일한 조건으로 다시 계산하여 일치·불일치·검증 불가를 반환하므로, 리포트를 수령한 쪽에서 위변조나 차이 여부를 확인할 수 있습니다.

0.9.0부터는 `grift actor`의 Markdown 최상단에 기록에서 드러나는 업무 진행 방식을 짧은 문장으로 서술합니다. 수정한 부분의 구분, 변경 속도, 테스트 작성 방식, 참여 형태에 대해 건수와 기간을 덧붙여 작성하며, 이어서 이 기록으로는 확인할 수 없는 점을 적고 면담에서 확인하고자 하는 사항을 질문 형태로 나열합니다. `grift project`은 프로젝트 저장소의 진행 방식을 동일한 규칙으로 서술하되 개인별 수치와 참여 형태는 출력하지 않습니다. `grift align`는 요구사항과 기록의 비교 목록에 면담에서 확인하고자 하는 사항을 질문 형태로 덧붙입니다. 문장과 질문은 공개된 [결정표](https://github.com/Cor-Incorporated/grift-cli/blob/v0.9.0/docs/trait-profile.md)에 따라 수치로부터 선택되며, AI는 사용하지 않습니다. JSON에는 포함되지 않으므로 `grift verify`으로 검산할 수 있는 대상은 문장의 바탕이 된 수치 쪽입니다.

인물에 관한 문장과 질문은 본인이 표기한 ID로 동의 기록이 있을 때만 출력합니다. 그 외의 경우에는 출력하지 않은 이유를 한 문장으로 기재합니다. 여러 인물을 취합하여 출력할 때(`--all`, `--top`)는 문장을 출력하지 않습니다.

기법의 명칭은 TEP(Technical Evidence Pipeline, 기술적 증거 도출 파이프라인)입니다. git 기록 읽기, 정해진 규칙에 따른 계수, 계수된 값에 분모 및 계수되지 않은 항목의 사유 병기, 누구나 동일한 절차로 다시 계산할 수 있도록 보장이라는 4단계로 구성됩니다. 상세한 설명은 Grift 사이트의 [TEP 페이지](https://griftai.org/tep)에서 확인하실 수 있습니다.

본 페이지와 griftai.org에서 사용하는 표현과 CLI가 출력에 사용하는 용어는 다음과 같이 대응됩니다.

| 사이트의 표현 | CLI 용어 |
|---|---|
| 검사값 | observed value(`kind: observed`. 값과 단위, 분모 표기) |
| 테스트 동시 수정률 | test co-change |
| 재작업률 | corrective rework |
| 재접촉 | path retouch |
| Code recency | survival(`--survival`를 지정했을 때만) |
| 저장소의 맥락 | context profile |
| 작업 영역·변경 리듬·검증 형태 | surface_profile / change_rhythm / verification_profile |

0.9.0부터는 CLI의 Markdown에서도 수정한 부분의 구분(작업 영역), 변경 속도(변경 리듬), 테스트 작성 방식(검증 형태), 참여 형태의 4가지 관점을 griftai.org와 동일한 명칭으로 서술합니다. JSON 키는 변경되지 않습니다.

## 성과

2026년 9월 8일, PyPI에 [v0.7.2](https://pypi.org/project/grift-cli/0.7.2/)를 출시했습니다. 지표는 공개된 117개 저장소에서 검증되었으며, 명확히 구분된 비교와 아직 구분되지 않은 비교를 모두 GitHub에 공개하고 있습니다(사내 측정 결과이며, 제3자에 의한 감사는 받지 않았습니다).

2026년 10월 25일, 사이트의 문구와 CLI의 출력을 한 줄씩 대조했습니다. 복수 인원 목록(`actor-index`)이 안내문에서는 "순위가 아니다"라고 명시하면서도 커밋 수가 많은 순으로 정렬되어 있었기 때문에, 2026년 10월 26일에 출시한 [0.8.0](https://github.com/Cor-Incorporated/grift-cli/releases/tag/v0.8.0)에서 정렬 기준을 ID 사전순으로 변경했습니다. 커밋 수 수치는 유지하고 있습니다. 경위와 0.8 계열에 적용되는 5가지 인수 조건은 [블로그 게시글](https://cor-jp.com/blog/grift-no-score-no-rank-in-code/)에 정리했습니다.

2026년 10월 27일에 출시한 [0.9.0](https://github.com/Cor-Incorporated/grift-cli/releases/tag/v0.9.0)에서는 앞서 언급한 리포트 서두 문장과 면담 질문을 추가했습니다. 아울러 경향의 "강도" 행과 대조의 "방향" 행을 Markdown에서 제외했습니다. 두 개의 리포트를 나란히 두었을 때 강한 사람·약한 사람, 적합한 사람·부적합한 사람으로 해석될 여지가 있었기 때문입니다. 인물에 대해 사실과 다른 수치가 산출될 수 있었던 4개 지점도 수정했습니다.

2026년 10월 28일에 출시한 [0.9.1](https://github.com/Cor-Incorporated/grift-cli/releases/tag/v0.9.1)에서는 0.9.0 이후 발견된, 인물이나 프로젝트에 대해 사실과 다른 수치가 산출될 수 있었던 지점을 수정했습니다. 신규 명령어는 없으며, 점수·순위·유형명을 출력하지 않는 원칙 또한 변함없습니다. 정의 버전이 변경되었으므로 0.9.0에서 저장된 리포트와 대조 결과는 0.9.1의 `grift verify`에서 검산할 수 없게 됩니다(요구사항만으로 생성한 프로젝트 리포트 등의 예외는 [마이그레이션 시 주의사항](https://github.com/Cor-Incorporated/grift-cli/blob/v0.9.1/docs/migration-v091.md)을 참조해 주십시오).

현재는 후보자 본인이 로컬 환경에서 실행한 기록을 바탕으로 추천 사유를 구체화하는 시범 도입(PoC) 준비를 소개 회사 및 SES 기업들과 진행하고 있습니다. 자체 개발 기업의 채용 담당자분들과도 후보자 본인이 공유한 기록을 통해 어떤 업무를 수행해 왔는지 검증하는 시범 도입(PoC) 문의를 받고 있습니다. 정식 버전은 시범 도입 결과를 바탕으로 2027년 제공 개시를 목표로 하고 있습니다. Grift는 [griftai.org](https://griftai.org)에서도 소개하고 있습니다.

Grift의 철학은 [Qiita](https://qiita.com/terisuke/items/c6bb68b3af0db3d43bb1) 및 [note](https://note.com/cor_instrument/n/nd58ba0955317) 게시글에서도 소개하고 있습니다.
