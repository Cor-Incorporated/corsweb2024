## 과제

인재 소개 회사나 SES의 영업 담당자는 후보자를 기업에 추천할 때 "왜 이 분을 추천하는지"를 설명해야 합니다. 그러나 손에 쥔 자료는 이력서와 면담에서의 인상이 대부분입니다. "Java 5년"이라고 적혀 있어도, 어떤 변경을 어떻게 확인하며 진행해 왔는지, 업무의 실질적인 내용까지는 전해지지 않습니다.

한편 GitHub 잔디나 커밋 수 같은 "활동량"은 생성형 AI나 에이전트를 사용하면 쉽게 부풀릴 수 있게 되었습니다. 양의 방대함은 이제 추천의 근거가 되기 어렵습니다. 그렇다고 해서 하나의 점수로 합산하면, 무엇을·어느 기간에·어떤 모수로 측정했는지가 사라져 서류 탈락의 도구로 사용되고 맙니다. 추천하는 측에게도, 추천받는 측에게도 "확인할 수 있는 자료"가 부족했습니다.

## 접근 방식

Grift는 2026년 2월, 수탁 개발 견적을 지원하는 웹 앱으로 시작되었습니다. 견적의 근거를 모색하는 과정에서, 가장 확실한 자료는 엔지니어가 축적해 온 git 이력 그 자체임을 깨닫고, 2026년 8월에 측정 부분을 커맨드 라인 도구로 독립시켰습니다. 9월에는 기존 웹 앱 제공을 중단하고, 인재 소개 회사·SES의 영업을 지원하는 방향으로 방침을 전환했습니다.

설계에서는 3가지 약속을 먼저 정했습니다.

- 점수화하지 않는다: 출력하는 것은 검사값이며, 판단하는 것은 사람이다. 종합 점수·순위·합불·등급은 매기지 않으며, 수치에는 반드시 분자와 분모를 명시한다
- 매번 동일한 결과: 측정에 AI(LLM)를 사용하지 않는다. 동일한 저장소, 동일한 버전이라면 누가 실행하더라도 동일한 수치가 나온다
- 어디에도 전송하지 않는다: 로컬 PC에서만 실행된다. 공유할지 여부, 어떤 저장소를 공개할지는 본인이 결정한다

이와 함께, "부재를 부정적으로 해석하지 않는다", "수치만으로 탈락시키지 않는다", "본인 동의 없이 타인을 측정하지 않는다" 등 7개 조항의 이용 규범을 수립하고, 이를 준수하지 않는 사용 방식은 기법의 이름(TEP: Technical Evidence Pipeline)으로 부르지 않기로 규정했습니다.

## 구현

Grift CLI는 git 이력만으로 다음과 같은 관측치를 추출합니다.

- 귀속 구분: 본인의 독자 커밋, 타인의 작업, 봇, 생성/벤더 산출물, fork 원본에서 이어받은 이력 등 11개 분류로 누구의 작업인지 구분
- 테스트 동시 수정률: 프로덕션 코드 변경과 동일한 커밋에서 테스트도 함께 변경한 비율
- 재작업률·재접촉: 최근에 작업한 파일의 재작업 및 재접촉 비율(경향을 기록한 것이며, 합불 판정에 사용하지 않음)
- 저장소의 맥락: 실제 작업 일수, 참여 인원수 및 최다 작성자의 점유율, 리뷰를 거친 비율 등

v0.6에서 추가된 `report-v2`에서는 한 엔지니어의 작업 방식을 살펴보는 레이어가 늘어났습니다. 모두 분자와 분모가 함께 제공되며, 직종이나 능력을 판정하는 것이 아닙니다.

- 작업 영역(`surface_profile`): test / docs / CI/CD / platform / data / observability / frontend / backend / config / 생성·벤더 / 기타의 11개 구분으로, 어떤 영역의 변경이 몇 건 있었는지
- 변경 리듬(`change_rhythm`): 최근 180일 중 변경을 제출한 일수와 제출 간격(중앙값 및 90퍼센타일, 2일 이내로 이어진 비율, 30일 이상 벌어진 비율). 노동 시간이나 의욕을 나타내는 것이 아닙니다
- 검증 형태(`verification_profile`): 테스트를 다룬 커밋의 비율과 그 종류(unit / integration / e2e / contract / 알 수 없음), fix 커밋에 테스트가 수반된 비율
- 역할의 4차원(`role_profile`): domain / work_type / time / process_position의 4가지만을 다루며, 하나의 직종으로 축약하지 않습니다. 본인 동의가 기록된 identity가 있을 때만 출력합니다

프로젝트 요건과의 대조 역시 순위를 매기지 않는 방식으로 진행됩니다. 프로젝트 측은 `grift project`에서 요구하는 영역·검증·리듬·입력을 선언하고, `grift align`가 후보자의 관측치와 축별로 나란히 배치합니다. 배열은 겹침(overlap)·범위 외(outside_declared_range)·0건(observed_zero)·미관측(not_observed)·요구 없음(not_declared)의 5가지 형태뿐이며, 종합 점수·순위·합불은 계산하지 않습니다. `--team`에서 팀 단위로 살펴볼 때는 요구를 충족하는 인원수만 출력하며, 3명 미만일 때는 개인이 특정되므로 집계하지 않습니다.

모수가 20 미만일 때는 비율을 산출하지 않고 건수만 표시하며, 관측되지 않은 항목은 "실적 없음"이 아닌 이유가 명시된 "미관측"으로 출력합니다. `grift verify` 은 저장된 리포트를 동일한 조건으로 다시 계산하여 일치·불일치·검증 불능을 반환하므로, 전달받은 측에서 변조나 불일치 여부를 확인할 수 있습니다.

0.9.0부터는 `grift actor`의 Markdown 도입부에 기록을 통해 알 수 있는 업무 진행 방식을 짧은 문장으로 서술합니다. 변경된 부분의 구분, 변경 페이스, 테스트 작성 방식, 참여 방식에 대해 건수와 기간을 덧붙여 서술하고, 이어서 이 기록으로는 알 수 없는 사항을 작성하며, 면담에서 확인하고자 하는 점을 질문 형태로 나열합니다. `grift project`은 프로젝트 저장소의 진행 방식을 동일한 규칙으로 작성하며, 개인별 수치와 참여 방식은 출력하지 않습니다. `grift align`는 요구 사항과 기록의 배열에, 면담에서 확인하고자 하는 점을 질문 형태로 덧붙입니다. 문장과 질문은 공개된 [결정표](https://github.com/Cor-Incorporated/grift-cli/blob/v0.9.0/docs/trait-profile.md)를 통해 수치로부터 선택되며, AI는 사용하지 않습니다. JSON에는 포함되지 않으므로, `grift verify`으로 검산할 수 있는 것은 문장의 근거가 된 수치 쪽입니다.

인물에 대한 문장과 질문은 본인이 표명한 ID이자 동의 기록이 있을 때만 출력합니다. 그 외의 경우에는 출력하지 않은 이유를 한 문장으로 서술합니다. 여러 인물을 한 번에 출력할 때(`--all`, `--top`)는 문장을 출력하지 않습니다.

기법의 이름은 TEP(Technical Evidence Pipeline, 기술적 증거를 추출하는 파이프라인)입니다. git 기록을 읽고, 정해진 규칙에 따라 카운트하며, 카운트한 값에 분모와 집계되지 못한 항목의 이유를 덧붙이고, 누구나 동일한 절차로 다시 카운트할 수 있도록 하는 4단계로 구성되어 있습니다. 상세한 설명은 Grift 사이트의 [TEP 페이지](https://griftai.org/tep)에 마련되어 있습니다.

본 페이지 및 griftai.org에서 사용하는 표현과 CLI가 출력에 기재하는 용어는 다음과 같이 대응됩니다.

| 사이트의 표현 | CLI 용어 |
|---|---|
| 검사값 | observed value(`kind: observed`. 값과 단위, 분모가 첨부됨) |
| 테스트 동시 수정률 | test co-change |
| 재작업률 | corrective rework |
| 재접촉 | path retouch |
| Code recency | survival(`--survival`를 지정했을 때만) |
| 저장소의 맥락 | context profile |
| 작업 영역·변경 리듬·검증 형태 | surface_profile / change_rhythm / verification_profile |

0.9.0부터는 CLI의 Markdown에서도 변경된 부분의 구분(작업 영역), 변경 페이스(변경 리듬), 테스트 작성 방식(검증 형태), 참여 방식이라는 4가지 관점을 griftai.org와 동일한 명칭으로 서술합니다. JSON의 키는 변경되지 않습니다.

0.9.2에서는 호스트에 Python을 설치하지 않고도, grift-cli 저장소로 만든 Docker 이미지를 통해 실행할 수 있도록 지원했습니다. 읽고자 하는 저장소는 이력을 전체 가져와 `/repo`에 전달합니다. `git worktree`로 생성된 작업 트리는 사용할 수 없습니다.

`grift update`은 실행 중인 환경만 업데이트하고, 업데이트 후에 적용된 버전을 표시하도록 변경했습니다. PATH에 있는 다른 환경은 사용하지 않습니다. `grift update --check`은 PyPI의 최신 버전 정보를 확인하기만 하며 업데이트는 수행하지 않습니다. 자동 업데이트 및 일반적인 측정 명령이 버전을 확인하는 통신은 존재하지 않습니다.

`grift contribute`는 본인 동의 후에 제출용 파일을 로컬에 저장합니다. 자동으로 전송하지는 않습니다. 기본 설정인 `--door local`으로 생성한 파일은 공개 수신 창구에 제출할 수 없으므로, 제출 ID·PR 내 파일명·meta 행은 표시되지 않으며, `--door public-pr`로 재생성하는 절차만 표시합니다. 공개하여 제출할 때는 재생성 실행 시 표시되는 제출 ID·PR 내 파일명·meta 행과 두 가지 제출 경로의 URL을 사용합니다. 본인이 직접 올리는 공개 PR이든, 신원을 밝히지 않는 대리 PR이든 파일의 내용은 공개됩니다.

## 성과

2026년 9월 8일에 PyPI에서 [v0.7.2](https://pypi.org/project/grift-cli/0.7.2/)를 공개했습니다. 지표는 공개되어 있는 117개 저장소에서 검증하였으며, 구분해 낸 비교와 아직 구분하지 못한 비교를 모두 GitHub에 공개하고 있습니다(사내 측정 결과이며, 제3자에 의한 감사는 받지 않았습니다).

2026년 10월 25일에 사이트의 문구와 CLI 출력을 한 줄씩 대조했습니다. 여러 인물의 목록(`actor-index`)이 주석에는 "순위가 아니다"라고 기재되어 있으면서도 커밋 수가 많은 순으로 정렬되어 있었기에, 2026년 10월 26일에 공개한 [0.8.0](https://github.com/Cor-Incorporated/grift-cli/releases/tag/v0.8.0)에서 정렬 기준을 ID의 사전순으로 변경했습니다. 커밋 수 수치는 유지하고 있습니다. 경위와 0.8 버전에 부과한 5가지 인수 조건은 [블로그 글](https://cor-jp.com/blog/grift-no-score-no-rank-in-code/)에 기록했습니다.

2026년 10월 27일에 공개한 [0.9.0](https://github.com/Cor-Incorporated/grift-cli/releases/tag/v0.9.0)에서 앞서 언급한 리포트 도입부의 문장과 면담 질문을 추가했습니다. 이와 함께 경향의 "강도" 행과 대조의 "적합 방향" 행을 Markdown에서 제외했습니다. 두 리포트를 나란히 놓았을 때 강한 사람·약한 사람, 잘 맞는 사람·맞지 않는 사람으로 해석될 여지가 있기 때문입니다. 인물에 관해 사실과 다른 수치가 나타날 수 있었던 부분도 4곳 수정했습니다.

2026년 10월 28일에 공개한 [0.9.1](https://github.com/Cor-Incorporated/grift-cli/releases/tag/v0.9.1)에서는 0.9.0 배포 이후 발견된 인물이나 프로젝트에 대해 사실과 다른 수치가 나타날 수 있었던 부분을 수정했습니다. 새로운 명령어는 추가되지 않았으며, 점수·순위·타입명을 출력하지 않는 점 또한 변함없습니다. 정의 버전이 변경됨에 따라 0.9.0에서 저장된 리포트와 대조 데이터는 0.9.1의 `grift verify`에서 검산할 수 없게 됩니다(요구 사항만으로 작성한 프로젝트 리포트 등의 예외는 [마이그레이션 주의 사항](https://github.com/Cor-Incorporated/grift-cli/blob/v0.9.1/docs/migration-v091.md)에 기재되어 있습니다).

[0.9.2](https://github.com/Cor-Incorporated/grift-cli/releases/tag/v0.9.2)에서는 `grift report`의 Markdown에 있는 저장소 맥락 란에 관측된 이력상 최초로 활동한 연도와 마지막으로 활동한 연도, 태그 빈도의 분자와 분모를 표시하도록 개선했습니다. JSON 값은 변경되지 않습니다. 현재도 활동 중인 사람에게도 마지막 활동 연도가 표시되므로, 이탈이나 퇴사를 나타내는 것이 아닙니다. 태그 빈도는 "태그 수 ÷ 활동 기간 일수 × 365.25"의 연간 환산 수치이며, 관측된 릴리스 횟수가 아닙니다. 활동 기간이 20일 미만인 저장소에서는 연간 환산하지 않고 태그 수와 일수만 표시합니다.

새로운 명령어는 추가되지 않았으며, 점수·순위·합불을 출력하지 않는 점 또한 변함없습니다. 분석 값을 변경하는 수정도 없으나, 정의 버전을 올렸기 때문에 0.9.1에서 저장된 리포트와 대조 데이터는 0.9.2의 `grift verify`에서 검산할 수 없게 됩니다(요구 사항만으로 작성한 프로젝트 리포트 등의 예외는 [마이그레이션 주의 사항](https://github.com/Cor-Incorporated/grift-cli/blob/v0.9.2/docs/migration-v092.md)에 기재되어 있습니다).

현재는 후보자 본인이 로컬에서 실행한 기록을 바탕으로 추천 이유를 구체화하는 시범 도입(PoC) 준비를 소개 회사 및 SES 기업들과 함께 진행하고 있습니다. 자체 서비스를 개발하는 기업의 채용 담당자분들로부터도 후보자 본인이 공유한 기록을 통해 어떤 업무를 수행해 왔는지 확인하는 시범 도입(PoC) 문의를 받고 있습니다. 정식 버전에 대해서는 시범 도입 결과를 바탕으로 2027년 서비스 개시를 목표로 하고 있습니다. Grift는 [griftai.org](https://griftai.org)에서도 소개하고 있습니다.

Grift의 철학은 [Qiita](https://qiita.com/terisuke/items/c6bb68b3af0db3d43bb1) 및 [note](https://note.com/cor_instrument/n/nd58ba0955317) 기사에서도 소개해 드리고 있습니다.
