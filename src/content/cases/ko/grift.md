## 과제

인재 소개 회사나 SES의 영업 담당자는 후보자를 기업에 추천할 때 "왜 이 분을 추천하는지"를 설명해야 합니다. 그러나 수중에 있는 자료는 이력서와 면담에서의 인상이 대부분입니다. "Java 5년"이라고 적혀 있어도, 어떤 변경을 어떻게 검증하며 진행해 왔는지, 일의 실질적인 내용까지는 전해지지 않습니다.

반면, GitHub 잔디나 커밋 수와 같은 "활동량"은 생성형 AI나 에이전트를 사용하면 쉽게 부풀릴 수 있게 되었습니다. 양의 방대함은 이제 추천의 근거가 되기 어렵습니다. 그렇다고 해서 하나의 점수로 종합하면 무엇을, 어느 기간 동안, 어떤 모수로 측정했는지가 사라져 서류 탈락의 도구로 사용되고 맙니다. 추천하는 쪽에서도, 추천받는 쪽에서도 "확인할 수 있는 자료"가 부족했습니다.

## 접근 방식

Grift는 2026년 2월, 수탁 개발 견적을 지원하는 웹 앱으로 시작되었습니다. 견적의 근거를 찾는 과정에서, 가장 확실한 자료는 엔지니어가 축적해 온 git 이력 그 자체라는 점을 깨닫고, 2026년 8월에 계측 부분을 커맨드라인 툴로 분리해 냈습니다. 9월에는 기존 웹 앱의 제공을 중단하고 인재 소개 회사·SES의 영업을 지원하는 방향으로 방침을 전환했습니다.

설계 단계에서 3가지 약속을 먼저 정했습니다.

- 점수화하지 않는다: 출력하는 것은 검사값이며, 판단하는 것은 사람. 종합 점수·순위·합불·등급은 매기지 않으며, 수치에는 반드시 분자와 분모를 부여한다
- 매번 동일한 결과: 계측에 AI(LLM)를 사용하지 않는다. 동일한 리포지토리, 동일한 버전이라면 누가 실행해도 같은 수치가 나온다
- 어디로도 전송하지 않는다: 로컬 PC에서만 동작한다. 공유할지 여부, 어떤 리포지토리를 공개할지는 본인이 결정한다

이와 함께 "부재를 부정적으로 해석하지 않는다", "수치만으로 탈락시키지 않는다", "본인 동의 없이 타인을 측정하지 않는다" 등 7개 조항의 이용 규범을 정하고, 이를 준수하지 않는 사용법은 해당 기법의 명칭(TEP: Technical Evidence Pipeline)으로 부르지 않기로 규정했습니다.

## 구현

Grift CLI는 오직 git 이력만을 바탕으로 다음과 같은 관측치를 추출합니다.

- 귀속 구분: 본인의 독자적 커밋, 타인의 작업, 봇, 생성형·벤더 산출물, fork 원본에서 이어받은 이력 등 11개 분류로 누구의 작업인지를 구분
- 테스트 동시 수정률: 프로덕션 코드 변경과 동일한 커밋에서 테스트도 함께 변경한 비율
- 재작업률·재접촉: 최근에 다룬 파일의 재작업이나 재접촉 비율(경향을 기록한 것이며, 합불 판정에는 사용하지 않음)
- 리포지토리의 맥락: 실제 작업 일수, 참여 인원수 및 최다 작성자의 점유율, 리뷰를 거친 비율 등

v0.6에서 추가된 `report-v2`에서는 한 엔지니어의 작업 형태를 살펴보는 계층이 늘어났습니다. 모두 분자와 분모가 함께 제공되며, 직종이나 능력에 대한 판정이 아닙니다.

- 작업 영역(`surface_profile`): test / docs / CI/CD / platform / data / observability / frontend / backend / config / 생성형·벤더 / 기타의 11개 구분으로, 어떤 영역의 변경이 몇 건 있었는지
- 변경 리듬(`change_rhythm`): 최근 180일 중 변경을 제출한 일수와 제출 간격(중앙값 및 90백분위수, 2일 이내에 연속된 비율, 30일 이상 비어 있던 비율). 노동 시간이나 의욕을 의미하지 않습니다
- 검증 형태(`verification_profile`): 테스트를 다룬 커밋의 비율과 그 종류(unit / integration / e2e / contract / 알 수 없음), fix 커밋에 테스트가 수반된 비율
- 역할의 4차원(`role_profile`): domain / work_type / time / process_position의 4가지만을 다루며, 하나의 직종으로 단일화하지 않습니다. 본인의 동의가 기록된 identity가 있을 때만 표시합니다

프로젝트 요건과의 대조 역시 순위를 매기지 않는 형태로 진행합니다. 프로젝트 측은 `grift project`을 통해 요구하는 영역·검증·리듬·입력을 선언하고, `grift align`가 후보자의 관측치와 각 축에 맞춰 나열합니다. 나열은 겹침(overlap)·범위 밖(outside_declared_range)·0건(observed_zero)·미관측(not_observed)·요구 없음(not_declared)의 5가지만으로 이루어지며, 종합 점수·순위·합불은 계산하지 않습니다. `--team`로 팀 단위로 살펴볼 때는 요구를 충족하는 인원수만 표시하며, 3명 미만일 경우 개인이 특정되므로 집계하지 않습니다.

모수가 20 미만일 때는 비율을 표시하지 않고 건수만 나타내며, 관측되지 않은 항목은 "실적 없음"이 아니라 이유가 명시된 "미관측"으로 출력합니다. `grift verify` 은 저장된 리포트를 동일한 조건으로 다시 계산하여 일치·불일치·검증 불가를 반환하므로, 이를 전달받은 측에서 변조나 불일치를 확인할 수 있습니다.

해당 기법의 명칭은 TEP(Technical Evidence Pipeline, 기술 증거 추출 파이프라인)입니다. git 기록을 읽고, 정해진 규칙에 따라 세고, 계산된 값에 분모와 집계되지 않은 항목의 이유를 덧붙이며, 누구나 동일한 절차로 다시 셀 수 있게 한다는 4단계로 구성되어 있습니다. 자세한 설명은 Grift 사이트의 [TEP 페이지](https://griftai.org/tep)에 나와 있습니다.

본 페이지 및 griftai.org에서 사용하는 표현과 CLI가 출력에 표기하는 용어는 다음과 같이 대응됩니다.

| 사이트 표기 | CLI 용어 |
|---|---|
| 검사값 | observed value(`kind: observed`. 값과 단위, 분모가 포함됨) |
| 테스트 동시 수정률 | test co-change |
| 재작업률 | corrective rework |
| 재접촉 | path retouch |
| Code recency | survival(`--survival`를 지정한 경우에만 해당) |
| 리포지토리의 맥락 | context profile |
| 작업 영역·변경 리듬·검증 형태 | surface_profile / change_rhythm / verification_profile |

- 배포: PyPI "grift-cli"(`pipx install grift-cli`, Python 3.11 이상)
- 라이선스: MIT
- 릴리스 노트: [github.com/Cor-Incorporated/grift-cli/releases](https://github.com/Cor-Incorporated/grift-cli/releases)(버전별 변경 사항)

## 성과

2026년 9월 8일, PyPI에 [v0.7.2](https://pypi.org/project/grift-cli/0.7.2/)를 출시했습니다. 지표는 공개된 117개의 리포지토리에서 검증했으며, 구별해 낸 비교와 아직 구별해 내지 못한 비교 모두 GitHub에 공개하고 있습니다(사내 측정 결과이며, 제3자 감사를 받은 것은 아닙니다).

2026년 10월 25일, 사이트의 문구와 CLI의 출력을 한 줄씩 대조했습니다. 복수 인원 목록(`actor-index`)이 안내 문구에는 "순위가 아니다"라고 적혀 있으면서도 커밋 수가 많은 순서로 정렬되어 있었기 때문에, 2026년 10월 26일에 출시된 [0.8.0](https://github.com/Cor-Incorporated/grift-cli/releases/tag/v0.8.0)에서 정렬 기준을 ID 사전순으로 변경했습니다. 커밋 수 수치는 유지하고 있습니다. 경위와 0.8 계열에 부여된 5가지 인수 조건은 [블로그 글](https://cor-jp.com/blog/grift-no-score-no-rank-in-code/)에 정리했습니다.

현재는 후보자 본인이 로컬 환경에서 실행한 기록을 바탕으로 추천 사유를 구체화하는 시범 도입(PoC) 준비를 인재 소개 회사 및 SES 기업들과 함께 진행하고 있습니다. 자체 서비스를 개발하는 기업의 채용 담당자분들로부터도 후보자 본인이 공유한 기록을 통해 어떤 업무를 수행해 왔는지 확인하는 시범 도입(PoC) 관련 상담을 받고 있습니다. 정식 버전에 대해서는 시범 도입 결과를 반영하여 2027년 제공 개시를 목표로 하고 있습니다. Grift는 [griftai.org](https://griftai.org)에서도 소개하고 있습니다.

Grift의 철학은 [Qiita](https://qiita.com/terisuke/items/c6bb68b3af0db3d43bb1) 및 [note](https://note.com/cor_instrument/n/nd58ba0955317) 기사에서도 소개하고 있습니다.
