## 과제

헤드헌팅 회사나 SES의 영업 담당자는 후보자를 기업에 추천할 때 "왜 이 분을 추천하는지"를 설명해야 합니다. 하지만 손에 쥐고 있는 자료는 이력서와 면담에서의 인상이 대부분입니다. "Java 5년"이라고 적혀 있어도 어떤 변경을 어떻게 검증하며 진행해 왔는지, 일의 실질적인 내용까지는 전달되지 않습니다.

반면, GitHub 잔디나 커밋 수 같은 "활동량"은 생성형 AI나 에이전트를 사용하면 쉽게 부풀릴 수 있게 되었습니다. 양의 방대함은 이제 추천의 근거가 되기 어렵습니다. 그렇다고 해서 하나의 점수로 종합하면 무엇을, 어느 기간 동안, 어떤 모수로 측정했는지가 사라져 서류 탈락의 도구로 악용되고 맙니다. 추천하는 쪽에도, 추천받는 쪽에도 "검증 가능한 자료"가 부족했습니다.

## 접근 방식

Grift는 2026년 2월, 외주 개발 견적을 지원하는 웹 앱으로 시작되었습니다. 견적의 근거를 찾는 과정에서 가장 확실한 자료는 엔지니어가 쌓아온 git 히스토리 그 자체임을 깨닫고, 2026년 8월에 측정 부분을 커맨드 라인 툴로 분리해 냈습니다. 9월에는 기존 웹 앱의 제공을 중단하고, 헤드헌팅 회사·SES 영업을 지원하는 방향으로 방침을 전환했습니다.

설계에 있어서는 3가지 약속을 먼저 정했습니다.

- 점수화하지 않는다: 제공하는 것은 검사값이며, 판단하는 것은 사람. 종합 점수·순위·합불·등급은 매기지 않고, 수치에는 반드시 분자와 분모를 명시한다
- 매번 일관된 결과: 측정에 AI(LLM)를 사용하지 않는다. 동일한 리포지토리, 동일한 버전이라면 누가 실행하더라도 같은 수치가 나온다
- 어디로도 전송하지 않는다: 로컬 PC에서만 동작한다. 공유할지 여부와 어떤 리포지토리를 공개할지는 본인이 결정한다

이와 함께 "부재를 부정적으로 해석하지 않는다", "수치만으로 서류 탈락시키지 않는다", "본인 동의 없이 타인을 측정하지 않는다" 등 7개 조항의 이용 규범을 마련하고, 이를 지키지 않는 사용 방식은 기법의 명칭(TEP: Technical Evidence Pipeline)으로 부르지 않기로 결정했습니다.

## 구현

Grift CLI는 오직 git 히스토리로부터 다음과 같은 관측치를 추출합니다.

- 귀속 구분: 본인의 독자적인 커밋, 타인의 작업, bot, 생성·벤더 산출물, fork 원본으로부터 인계받은 히스토리 등 11개 분류로 누구의 작업인지 구분
- 테스트 동시 수정률: 프로덕션 코드 변경과 동일한 커밋에서 테스트도 함께 변경한 비율
- 재작업률·재접촉: 최근 수정한 파일의 재작업 및 재접촉 비율(경향을 기록한 것이며, 합불 판정에는 사용하지 않음)
- 리포지토리 컨텍스트: 실제 활동 일수, 참여 인원수 및 최다 작성자의 점유율, 리뷰를 거친 비율 등

v0.6에서 추가된 `report-v2`에서는 한 엔지니어의 작업 형태를 살펴보는 계층이 확장되었습니다. 모두 분자와 분모가 함께 제공되며, 직종이나 역량을 판정하는 것이 아닙니다.

- 작업 영역(`surface_profile`): test / docs / CI/CD / platform / data / observability / frontend / backend / config / 생성·벤더 / 기타 11개 구분으로, 어떤 영역의 변경이 몇 건 있었는지
- 변경 리듬(`change_rhythm`): 최근 180일 중 변경을 제출한 일수와 제출 간격(중앙값 및 90퍼센타일, 2일 이내에 이어진 비율, 30일 이상 벌어진 비율). 근무 시간이나 의욕을 의미하지 않습니다
- 검증 형태(`verification_profile`): 테스트를 다룬 커밋 비율과 그 종류(unit / integration / e2e / contract / 불명), fix 커밋에 테스트가 수반된 비율
- 역할의 4차원(`role_profile`): domain / work_type / time / process_position의 4가지만으로 구성되며, 하나의 직종으로 환원하지 않습니다. 본인의 동의가 기록된 identity가 있을 때만 출력합니다

프로젝트 요건과의 대조 역시 순위를 매기지 않는 방식으로 수행합니다. 프로젝트 측은 `grift project`을 통해 요구하는 영역·검증·리듬·입력을 선언하고, `grift align`는 후보자의 관측치와 축별로 나란히 배치합니다. 정렬 상태는 중복(overlap)·범위 외(outside_declared_range)·0건(observed_zero)·미관측(not_observed)·요구 없음(not_declared)의 5가지만 존재하며, 종합 점수·순위·합불은 계산하지 않습니다. `--team`를 통해 팀 단위로 살펴볼 때는 요구를 충족하는 인원수만 출력하며, 3명 미만인 경우 개인이 특정될 우려가 있어 집계하지 않습니다.

모수가 20 미만일 때는 비율을 산출하지 않고 건수만 표시하며, 관측되지 않은 항목은 "실적 없음"이 아니라 사유를 명시한 "미관측"으로 출력합니다. `grift verify` 은 저장된 리포트를 동일한 조건으로 다시 계산하여 일치·불일치·검증 불가를 반환하므로, 리포트를 수령한 측에서 변조나 불일치를 확인할 수 있습니다.

0.9.0부터는 `grift actor`의 Markdown 상단에 기록을 통해 파악할 수 있는 업무 진행 방식을 짧은 문장으로 기재합니다. 변경한 부분의 구분, 변경 페이스, 테스트 작성 방식, 참여 방식에 대해 건수와 기간을 덧붙여 서술하고, 이어서 이 기록으로는 확인할 수 없는 점을 적은 뒤 면담에서 확인하고자 하는 사항을 질문 형태로 나열합니다. `grift project`은 프로젝트 리포지토리의 진행 방식을 동일한 규칙으로 기재하며, 인원별 수치와 참여 방식은 출력하지 않습니다. `grift align`는 요구사항과 기록의 비교 목록에 면담에서 확인하고자 하는 사항을 질문 형태로 덧붙입니다. 문장과 질문은 공개된 [결정표](https://github.com/Cor-Incorporated/grift-cli/blob/v0.9.0/docs/trait-profile.md)를 기반으로 수치에서 도출되며, AI는 사용하지 않습니다. JSON에는 포함되지 않으므로, `grift verify`로 검산할 수 있는 것은 문장의 근거가 된 수치 쪽입니다.

인물에 관한 문장과 질문은 본인이 표명한 ID이며 동의 기록이 있을 때만 출력합니다. 그 외의 경우에는 출력하지 않는 이유를 한 문장으로 기재합니다. 여러 인물을 한꺼번에 출력할 때(`--all`, `--top`)는 문장을 출력하지 않습니다.

기법의 명칭은 TEP(Technical Evidence Pipeline, 기술적 근거를 추출하는 파이프라인)입니다. git 기록 읽기, 정해진 규칙에 따라 카운트하기, 산출된 값에 분모와 집계되지 않은 사유 기재하기, 누구나 동일한 절차로 다시 계산할 수 있도록 하기의 4단계로 구성됩니다. 자세한 설명은 Grift 사이트의 [TEP 페이지](https://griftai.org/tep)에 안내되어 있습니다.

본 페이지 및 griftai.org에서 사용하는 표현과 CLI가 출력에 기재하는 용어는 다음과 같이 대응됩니다.

| 사이트 표현 | CLI 용어 |
|---|---|
| 검사값 | observed value(`kind: observed`. 값과 단위 및 분모가 포함됨) |
| 테스트 동시 수정률 | test co-change |
| 재작업률 | corrective rework |
| 재접촉 | path retouch |
| Code recency | survival(`--survival`를 지정했을 때만) |
| 리포지토리 컨텍스트 | context profile |
| 작업 영역·변경 리듬·검증 형태 | surface_profile / change_rhythm / verification_profile |

0.9.0부터는 CLI의 Markdown 역시 변경한 부분의 구분(작업 영역), 변경 페이스(변경 리듬), 테스트 작성 방식(검증 형태), 참여 방식의 4가지 관점을 griftai.org와 동일한 명칭으로 기재합니다. JSON 키는 변경되지 않습니다.

## 성과

2026년 9월 8일, PyPI에 [v0.7.2](https://pypi.org/project/grift-cli/0.7.2/)를 공개했습니다. 지표는 공개되어 있는 117개 리포지토리에서 검증하였으며, 구분해 낸 비교와 아직 구분하지 못한 비교를 모두 GitHub에 공개하고 있습니다(사내 측정 결과이며, 제3자에 의한 감사는 받지 않았습니다).

2026년 10월 25일에는 사이트의 문구와 CLI 출력을 한 줄씩 대조했습니다. 여러 명의 목록(`actor-index`)이 주석으로는 "순위가 아니다"라고 명시하면서도 커밋 수가 많은 순으로 정렬되어 있었기 때문에, 2026년 10월 26일에 공개한 [0.8.0](https://github.com/Cor-Incorporated/grift-cli/releases/tag/v0.8.0)에서 정렬 기준을 ID의 사전순으로 변경했습니다. 커밋 수 수치는 유지하고 있습니다. 경위와 0.8 버전에 적용되는 5가지 인수 조건은 [블로그 글](https://cor-jp.com/blog/grift-no-score-no-rank-in-code/)에 정리했습니다.

2026년 10월 27일에 공개한 [0.9.0](https://github.com/Cor-Incorporated/grift-cli/releases/tag/v0.9.0)에서는 위에서 서술한 리포트 상단 문장과 면담 질문을 추가했습니다. 아울러 경향의 "강도" 행과 대조의 "적합 방향" 행을 Markdown에서 제외했습니다. 두 리포트를 나란히 놓았을 때 강한 사람·약한 사람, 적합한 사람·부적합한 사람으로 해석될 여지가 있기 때문입니다. 인물에 관해 사실과 다른 수치가 출력될 수 있던 부분도 4곳 수정했습니다.

2026년 10월 28일에 공개한 [0.9.1](https://github.com/Cor-Incorporated/grift-cli/releases/tag/v0.9.1)에서는 0.9.0 이후 발견된, 인물이나 프로젝트에 대해 사실과 다른 수치가 출력될 수 있었던 부분을 수정했습니다. 새로운 명령어는 없으며, 점수·순위·유형명을 출력하지 않는 방침 역시 동일합니다. 정의 버전이 변경되었기 때문에 0.9.0에서 저장된 리포트는 0.9.1의 `grift verify`로 검산할 수 없습니다.

현재는 후보자 본인이 로컬 환경에서 실행한 기록을 바탕으로 추천 사유를 구체화하는 시범 도입(PoC) 준비를 헤드헌팅 회사 및 SES 기업 여러분과 진행하고 있습니다. 자체 프로덕트를 개발하는 기업의 채용 담당자분들로부터도 후보자 본인이 공유한 기록을 통해 어떤 업무를 수행해 왔는지 확인하는 시범 도입(PoC) 문의를 받고 있습니다. 정식 버전은 시범 도입 결과를 반영하여 2027년 제공 시작을 목표로 하고 있습니다. Grift는 [griftai.org](https://griftai.org)에서도 소개하고 있습니다.

Grift의 철학은 [Qiita](https://qiita.com/terisuke/items/c6bb68b3af0db3d43bb1) 및 [note](https://note.com/cor_instrument/n/nd58ba0955317) 글에서도 소개하고 있습니다.
