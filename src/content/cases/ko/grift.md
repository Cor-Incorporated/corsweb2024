## 과제

인재 소개 회사나 SES의 영업 담당자는 기업에 후보자를 추천할 때 "왜 이 분을 추천하는지" 설명해야 합니다. 그러나 수중에 있는 자료는 이력서와 면담에서의 인상이 대부분입니다. "Java 5년"이라고 적혀 있어도 어떤 변경을 어떻게 확인하며 진행해 왔는지, 업무의 실질적인 내용까지는 전달되지 않습니다.

반면, GitHub 잔디나 커밋 수 같은 "활동량"은 생성형 AI나 에이전트를 사용하면 쉽게 부풀릴 수 있게 되었습니다. 양의 방대함은 더 이상 추천의 근거가 되기 어렵습니다. 그렇다고 해서 하나의 점수로 통합하면 무엇을, 어느 기간 동안, 어떤 모수를 바탕으로 측정했는지가 사라져 단순 필터링 도구로 사용되어 버립니다. 추천하는 측도, 추천받는 측도 '확인할 수 있는 자료'가 부족했습니다.

## 접근 방식

Grift는 2026년 2월, 수주 개발 견적을 지원하는 웹 앱으로 시작되었습니다. 견적의 근거를 찾는 과정에서 가장 확실한 자료는 엔지니어가 축적해 온 git 이력 자체라는 점을 깨닫고, 2026년 8월에 측정 부분을 커맨드라인 툴로 분리했습니다. 9월에는 기존 웹 앱의 제공을 중단하고 인재 소개 회사·SES의 영업을 지원하는 방향으로 방침을 전환했습니다.

설계 단계에서 세 가지 약속을 미리 정했습니다.

- 점수화하지 않는다: 산출하는 것은 검사값이며, 판단하는 것은 사람이다. 종합 점수·순위·합불·등급은 산출하지 않으며, 수치에는 반드시 분자와 분모를 부여한다.
- 매번 동일한 결과: 측정에 AI(LLM)를 사용하지 않는다. 동일한 저장소, 동일한 버전이라면 누가 실행하든 동일한 수치가 나온다.
- 어디에도 전송하지 않는다: 로컬 PC에서만 동작한다. 공유 여부나 어떤 저장소를 공개할지는 본인이 결정한다.

이와 함께 '부재를 부정적으로 해석하지 않는다', '수치만으로 잘라내지 않는다', '본인 동의 없이 타인을 측정하지 않는다' 등 7개 조항의 이용 규범을 정하고, 이를 준수하지 않는 사용 방식은 기법의 명칭(TEP: Technical Evidence Pipeline)으로 부르지 않기로 규정했습니다.

## 구현

Grift CLI는 git 이력만을 바탕으로 다음과 같은 관측치를 추출합니다.

- 귀속 구분: 본인의 독자 커밋, 타인의 작업, bot, 생성물·벤더 산출물, fork 원본에서 이어받은 이력 등 11개 분류로 누구의 작업인지 구분
- 테스트 동시 수정률: 프로덕션 코드 변경과 동일한 커밋에서 테스트도 변경된 비율
- 재작업률·재접촉: 최근 수정한 파일의 재작업 및 재접촉 비율(경향을 기록하는 것이며, 합불 판정에 사용하지 않음)
- 저장소의 맥락: 실작업 일수, 참여 인원 및 최다 작성자의 점유율, 리뷰를 거친 비율 등

v0.6에서 추가된 `report-v2`에서는 한 엔지니어의 업무 형태를 살펴보는 계층이 늘어났습니다. 모두 분자와 분모가 포함되어 있으며, 직종이나 역량을 판정하는 것이 아닙니다.

- 작업 영역(`surface_profile`): test / docs / CI/CD / platform / data / observability / frontend / backend / config / 생성물·벤더 / 기타 11개 구분으로, 어떤 영역의 변경이 몇 건 있었는지
- 변경 리듬(`change_rhythm`): 최근 180일 중 변경을 제출한 일수와 제출 간격(중앙값 및 90퍼센타일, 2일 이내로 이어진 비율, 30일 이상 비어 있던 비율). 노동 시간이나 의욕을 의미하지 않습니다.
- 검증 형태(`verification_profile`): 테스트를 수정한 커밋 비율 및 그 유형(unit / integration / e2e / contract / 불명), fix 커밋에 테스트가 수반된 비율
- 역할의 4차원(`role_profile`): domain / work_type / time / process_position의 4가지만을 다루며, 단일 직종으로 축약하지 않습니다. 본인의 동의가 기록된 identity가 있을 때만 산출합니다.

프로젝트 요건과의 대조 역시 순위를 매기지 않는 방식으로 진행합니다. 프로젝트 측은 `grift project`을 통해 요구하는 영역·검증·리듬·입력을 선언하고, `grift align`가 후보자의 관측치와 축별로 나란히 배치합니다. 배열은 겹침(overlap)·선언 범위 외(outside_declared_range)·0건(observed_zero)·미관측(not_observed)·요구 없음(not_declared)의 5가지로만 나뉘며, 종합 점수·순위·합불은 계산하지 않습니다. `--team`로 팀 단위로 살펴볼 때는 요구를 충족하는 인원수만 산출하며, 3인 미만인 경우 개인이 특정되므로 집계하지 않습니다.

모수가 20 미만일 때는 비율을 내지 않고 건수만 표기하며, 관측할 수 없었던 항목은 '실적 없음'이 아니라 사유를 덧붙인 '미관측'으로 표시합니다. `grift verify` 은 저장된 리포트를 동일한 조건으로 다시 계산하여 일치·불일치·검증 불가를 반환하므로, 리포트를 수령한 측에서 변조나 불일치를 직접 확인할 수 있습니다.

0.9.0부터는 `grift actor`의 Markdown 도입부에 기록을 통해 드러나는 업무 진행 방식을 짧은 문장으로 기재합니다. 변경된 부분의 구분, 변경 속도, 테스트 작성 방식, 참여 형태에 대해 건수와 기간을 덧붙여 작성하며, 이어서 이 기록으로는 확인할 수 없는 사항을 적고, 면담에서 확인하고자 하는 점을 질문 형태로 나열합니다. `grift project`은 프로젝트 저장소의 진행 방식을 동일한 규칙에 따라 기재하며, 개인별 수치와 참여 형태는 산출하지 않습니다. `grift align`는 요구사항과 기록의 비교 목록에 면담에서 확인하고자 하는 질문을 함께 첨부합니다. 문장과 질문은 공개된 [결정표](https://github.com/Cor-Incorporated/grift-cli/blob/v0.9.0/docs/trait-profile.md)를 기반으로 수치에서 도출되며, AI는 사용하지 않습니다. JSON에는 포함되지 않으므로, `grift verify`로 재검산할 수 있는 대상은 문장의 바탕이 된 수치 쪽입니다.

인물에 대한 문장과 질문은 본인이 명시한 ID이며 동의 기록이 있는 경우에만 산출합니다. 그렇지 않은 경우에는 산출하지 않는 사유를 한 문장으로 기재합니다. 여러 인물을 한데 모아 산출할 때(`--all`, `--top`)는 문장을 산출하지 않습니다.

이 기법의 명칭은 TEP(Technical Evidence Pipeline, 기술적 증거를 추출하는 파이프라인)입니다. git 기록 읽기, 정해진 규칙에 따라 계량하기, 계량된 값에 분모와 계량되지 못한 항목의 사유 부여하기, 누구나 동일한 절차로 재계량할 수 있도록 하기의 4단계로 구성되어 있습니다. 자세한 설명은 Grift 사이트의 [TEP 페이지](https://griftai.org/tep)에서 확인하실 수 있습니다.

본 페이지 및 griftai.org에서 사용하는 표현과 CLI 출력에 사용되는 용어는 다음과 같이 대응됩니다.

| 사이트의 표현 | CLI 용어 |
|---|---|
| 검사값 | observed value(`kind: observed`. 값, 단위, 분모 표기) |
| 테스트 동시 수정률 | test co-change |
| 재작업률 | corrective rework |
| 재접촉 | path retouch |
| Code recency | survival(`--survival`를 지정한 경우에만) |
| 저장소의 맥락 | context profile |
| 작업 영역·변경 리듬·검증 형태 | surface_profile / change_rhythm / verification_profile |

0.9.0부터는 CLI의 Markdown에서도 변경된 부분의 구분(작업 영역), 변경 속도(변경 리듬), 테스트 작성 방식(검증 형태), 참여 형태의 4가지 관점을 griftai.org와 동일한 명칭으로 표기합니다. JSON 키는 변경되지 않습니다.

## 성과

2026년 9월 8일, PyPI에 [v0.7.2](https://pypi.org/project/grift-cli/0.7.2/)를 출시했습니다. 지표는 공개된 117개 저장소에서 검증하였으며, 유의미한 차이를 구별해 낸 비교와 아직 구별해 내지 못한 비교 모두 GitHub에 공개되어 있습니다(사내 측정 결과이며, 제3자 감사는 거치지 않았습니다).

2026년 10월 25일에는 사이트 문구와 CLI 출력을 한 줄씩 대조했습니다. 여러 명의 목록(`actor-index`)이 주석에는 '순위가 아니다'라고 명시되어 있으면서도 커밋 수가 많은 순서로 정렬되어 있었기 때문에, 2026년 10월 26일 배포된 [0.8.0](https://github.com/Cor-Incorporated/grift-cli/releases/tag/v0.8.0)에서 정렬 방식을 ID의 사전순으로 변경했습니다. 커밋 수 수치는 유지하고 있습니다. 경위와 0.8 버전에 부과된 5가지 인수 조건은 [블로그 글](https://cor-jp.com/blog/grift-no-score-no-rank-in-code/)에 정리되어 있습니다.

2026년 10월 27일 공개된 [0.9.0](https://github.com/Cor-Incorporated/grift-cli/releases/tag/v0.9.0)에서는 앞서 언급된 리포트 도입부 문장과 면담 질문을 추가했습니다. 아울러 경향의 '강도' 행과 대조의 '방향' 행을 Markdown에서 제외했습니다. 두 개의 리포트를 나란히 놓았을 때 강한 사람·약한 사람, 적합한 사람·부적합한 사람으로 해석될 여지가 있었기 때문입니다. 사람과 관련하여 사실과 다른 수치가 나타날 수 있었던 부분 4곳도 수정했습니다.

현재는 후보자 본인이 로컬 환경에서 실행한 기록을 바탕으로 추천 근거를 구체화하는 시범 도입(PoC) 준비를 인재 소개 회사 및 SES 기업들과 함께 진행하고 있습니다. 자체 서비스를 개발하는 기업의 채용 담당자분들로부터도 후보자 본인이 공유한 기록을 통해 어떤 업무를 수행해 왔는지 확인하기 위한 시범 도입(PoC) 상담을 접수하고 있습니다. 정식 버전은 시범 도입 결과를 바탕으로 2027년 제공 개시를 목표로 하고 있습니다. Grift는 [griftai.org](https://griftai.org)에서도 소개해 드리고 있습니다.

Grift의 철학은 [Qiita](https://qiita.com/terisuke/items/c6bb68b3af0db3d43bb1) 및 [note](https://note.com/cor_instrument/n/nd58ba0955317) 기사를 통해서도 소개하고 있습니다.
